# 第一阶段执行清单（4 周）

> 这是开工第一步的工作单。**目标不是"写出功能"，而是用最小的代价把最不确定的几件事问清楚。**
>
> 四周之后你应该能回答三个问题：
> 1. 这套东西在 AGP 9 上建得起来吗？（技术前提）
> 2. 日志该怎么显示、怎么过滤才真好用？（最难的设计决策）
> 3. **外面的人到底会不会装？**（决定后面半年会不会白干）
>
> 全篇说人话。每件事都带"怎么算通过"和"产出物"。

---

## 为什么第一步是干这些，而不是写代码

因为现在有三件事是**猜**的，而它们都会决定架构：

| 假设 | 如果猜错了会怎样 |
|---|---|
| "外部用户会想要按链路串起来的日志" | 半年后做完了没人装 |
| "标签里塞来源和链路，看起来还行" | 天天用的东西难用，你自己先放弃 |
| "跨平台库在 AGP 9 上能建起来" | 模块结构推倒重来 |

**这三件事都只要几天就能问清楚，而写代码要几个月。所以先问，再写。**

### 任务 1.4 单模块 App 能不能无痛接入（1 天）

**做什么**：写一个最小的示范——极简到只有 `logcat` 输出，放在 `app` 模块里，确认**一个只有单个模块的普通 App，接入时不需要理解"组件""模块"这类概念**。

**为什么**：这是约束 18 的验收方式。外部用户大多数没有组件化架构，如果接入第一步就要他们注册"来源身份"，人就被劝退了。

**怎么算通过**：接入代码里**没有出现"组件""模块""来源注册"这类必须理解的概念**，也能跑起来打出日志。

**产出物**：一段在 `app` 里的示范 + 记录"接入需要几步、每步要理解什么"。

## 第 2 周：标签方案实测（最值钱的一周）

**这是整个第一阶段最重要的一件事。**

### 任务 2.1 把三种配方做成可切换的（3 天）

**背景已更新**：标签**已经决定做成可自定义**（决策见 `docs/records/05-标签方案决策.md`）。所以这一步不再是"三种里选一个对的"，而是——**三种都做出来、都能切换，只为"选默认值"下结论**。

三种配方：

| 配方 | 标签长什么样 | 上下文（链路/会话）放哪 |
|---|---|---|
| **A** | `Net/OkHttpClient` | 不放 |
| **B** | `Net/OkHttpClient` | 放在正文开头做前缀，比如 `[a3f9] ...` |
| **C** | `Net/OkHttpClient` | 只做结构化字段，正文和标签都不显示 |

**做什么**：同一个业务场景（模拟一次"下单"，跨界面、业务、网络三个来源，打 5 条日志）三种配方各打一遍。

**注意两点**：
1. 小样代码写完就可以扔，不要花时间做质量；
2. **链路号绝对不要放进标签**——每条都不同，标签会膨胀成几千个，过滤器就废了（原因见决策记录第二节）。

### 任务 2.2 在真机日志窗口里对比（1 天）

**怎么比**（在安卓 Studio 的日志窗口里逐项看）：

| 看什么 | 怎么算好 |
|---|---|
| 一屏能放下多少条 | 方案 A/B 应该差不多；如果 B 的前缀太长导致换行，就是减分 |
| 按来源过滤 | 点一下标签就能只看"网络"，三个方案都要做到 |
| **按链路过滤** | 这是关键：方案 B 靠关键字能过滤；**方案 C 很可能根本过滤不了**——因为日志窗口不认识你的结构化字段 |
| 视觉噪音 | 前缀是否让人看正文更累 |

**我预判的结论（要靠实测确认）**：**方案 C 在第一版的日志窗口里是"看不见"的**——上下文进了结构化字段但窗口不认识，等于白记。所以第一版要么用 B 过渡，要么给 C 配一个自己的查看方式（那是第二版的事）。

**如果实测确认了这一点，就是本阶段最有价值的发现**：它意味着"标签里必须有足够信息"这条约束是真的，后面所有格式化设计都按这个来。

**产出物**：三种方案的截图（同一个场景）+ 一张对比表 + 结论。

### 任务 2.3 定下默认配方（1 天）

**做什么**：按实测结果**定下默认配方**——注意不是"排除另外两个"，它们会作为可选项保留（标签已决定做成可自定义）。

**产出物**：把实测截图和结论补进 `docs/records/05-标签方案决策.md` 第五节。

## 第 3 周：接口标准初稿

### 任务 3.1 定接口的形状（2 天）

**做什么**：写一版**对外接口的初稿**（先写文档，不写实现）。必须想清楚这几件事：

| 要定的 | 为什么要现在定 |
|---|---|
| 怎么打日志（函数长什么样、消息是否惰性求值） | 惰性求值是性能的一半答案，且改起来影响所有调用点 |
| 怎么声明"来源" | 约束 18：必须可选、用户自定义名字 |
| 怎么设置级别（来源级 + 全局覆盖） | 两级开关是组件化架构的刚需 |
| 上下文怎么带（链路号、会话号） | 约束：开发者只在入口标一次 |
| 没初始化时的行为 | 约束 19：不许崩 |
| 出错怎么让用户知道 | 约束 19：不许静默吞 |

**为什么要写文档而不是直接写代码**：因为**对外用户意味着接口一旦发出去就基本改不动**。写文档改起来便宜，写代码改起来贵。

**怎么算通过**：一个不认识这个项目的人读完这份文档，能说出"我要怎么用它"，并且能指出哪些地方他没看懂。

### 任务 3.2 定死"不变量"（1 天）

**做什么**：从 `docs/架构设计约束-日志组件.md` 附录里挑出**第一版就要守**的那批（第 8 章有分批表），逐条确认：这条在第一版真的守得住吗？守不住就现在改范围。

**产出物**：`docs/records/07-第一版不变量.md`（只列第一版要守的，加一句"怎么验收"）。

### 任务 3.3 目录与包结构定稿（1 天）

**做什么**：按模块划分表，确认第一版**实际要建哪几个包**（不要把所有分支目录都预建空模块）。

**建议**：第一版先放在 `TLogger` 一个模块里，用包名区分（`com.tlogger`、`com.tlogger.output`…），**等真正需要单独发布某个部分时再拆模块**。

### 任务 3.4 支持矩阵过一遍 PR 式自检（1 天）

**做什么**：拿第 1 周的支持矩阵，对着接口初稿过一遍："这个接口在最低支持的版本上能用吗"。

## 第 4 周：客观证据 + 定下"成功"的客观标准

**原计划的"找外部开发者访谈"已取消。** 发起人的判断是："这个东西十个人十个答案。"

这个判断是对的——**日志显示偏好是主观的**，访谈除了收到一堆互相矛盾的意见，得不到可靠结论；而且为了迁就受访者的口味去改设计，反而会做出谁都不满意的折中品。

**换成三件客观的事：数真实代码、翻别人的抱怨、定自己能验证的标准。**

### 任务 4.1 统计真实代码里的日志用法（2 天）

**做什么**：拿现成的代码当样本，统计**日志到底是怎么被写的**：

- **样本**：自己项目（本仓库的 `app`、TRouterDemo 各模块）+ 2 到 3 个开源安卓项目
- **统计什么**：
  - 日志调用总数（`Log.*`、`Timber.*` 及其他库）
  - 有多少条是纯调试输出（消息里只有常量或简单变量）
  - 有多少条带了上下文（用户、请求、页面等信息）
  - 有多少条打在"循环或高频路径"里（只有这类对性能敏感）

**为什么这么做**：这是**客观数字，不是意见**。它直接回答两个此前只能靠猜的问题——"大家到底需不需要上下文"和"性能到底有多少人在乎"。

**怎么算通过**：给出具体数字（样本量、总调用数、各类占比），并且这个数字**能支持或推翻我们的假设**。如果数字推翻了假设，那也是一次成功的验证。

### 任务 4.2 翻现有库的 issue，看用户已经抱怨过什么（1 天）

**做什么**：在 Timber、Kermit、kmp-logcat、xLog 这些库的 issue 区按关键词翻（过滤、标签、上下文、链路、崩溃、丢日志、体积…），把**已经有人用文字提过的需求**记下来，附链接。

**为什么这么做**：这些是用户**已经真实表达过**的需求，比访谈里现编的回答可信得多；而且能看出哪些抱怨是反复出现的。

**注意**：只记"反复出现的"，单条不算数。

### 任务 4.3 定下"什么算成功"的客观标准（2 天）

原计划里"什么算成功"是靠访谈回答的，现在改成**自己能验证的四条**：

| 标准 | 怎么验证 | 什么时候能看到 |
|---|---|---|
| **我自己回不去** | 输出端地基做完后，把自己的项目切过来**连续用两周**；两周后如果主动想切回去，就是失败 | 第二阶段结束 |
| **接入不超过 10 分钟** | 从零建一个空工程，接入并打出第一条带来源和链路的日志，计时 | 第二阶段结束 |
| **打码不误伤** | 自己的项目跑一周，看有没有把正常日志改坏 | 第三阶段结束 |
| **找一条日志不超过 10 秒** | 在一次跨 3 个来源的操作里，只凭日志说出"这次操作发生了什么" | 第四阶段结束 |

**为什么用这四条**：它们都可验证、都不依赖别人的意见。其中"**我自己回不去**"这一条，比一百个人的礼貌回答都有说服力——**如果连你自己用完都不想留着，那就不该继续做。**

### 任务 4.4 Go / No-Go 判断（1 天）

四周结束做判断。**触发条件全部基于客观证据**：

| 结论 | 触发条件 | 下一步 |
|---|---|---|
| **Go（按计划）** | 构建通过（技术前提成立）+ 统计显示"带上下文的日志"占比不低 + issue 里能翻到反复出现的相关抱怨 | 进第二阶段（输出端地基） |
| **转向：只做打码** | 统计显示日志几乎都是纯调试输出（没人需要上下文），但隐私问题确实存在 | 第一版砍成"打码 + 编译期检查"，3 个月出货 |
| **降级：只做自用** | 证据不足，但你自己确实需要 | 按自己的需求做，不追外部采用，范围砍到最小 |
| **No-Go** | 技术前提不成立（跨平台结构建不起来）且没有替代方案 | 停下，写清原因 |

**产出物**：`docs/records/10-第一阶段结论.md`（**附数字和链接，不是感想**）。
