# 第一阶段执行清单（4 周）

> 这是开工第一步的工作单。**目标不是"写出功能"，而是用最小的代价把最不确定的几件事问清楚。**
>
> 四周之后你应该能回答三个问题：
> 1. 这套东西在 AGP 9 上建得起来吗？（技术前提）
> 2. 日志该怎么显示、怎么过滤才真好用？（最难的设计决策）
> 3. **外面的人到底会不会装？**（决定后面半年会不会白干）
>
> 全篇说人话。每件事都带"怎么算通过"和"产出物"。

---

## 为什么第一步是干这些，而不是写代码

因为现在有三件事是**猜**的，而它们都会决定架构：

| 假设 | 如果猜错了会怎样 |
|---|---|
| "外部用户会想要按链路串起来的日志" | 半年后做完了没人装 |
| "标签里塞来源和链路，看起来还行" | 天天用的东西难用，你自己先放弃 |
| "跨平台库在 AGP 9 上能建起来" | 模块结构推倒重来 |

**这三件事都只要几天就能问清楚，而写代码要几个月。所以先问，再写。**

## 第 1 周：把地基和前提确认掉

### 任务 1.1 构建验证（0.5 天）

**做什么**：在你的终端里跑一次构建。

```
cd ~/Work/Android/TLoggerDemo && ./gradlew :TLogger:build
```

**怎么算通过**：
- `BUILD SUCCESSFUL`
- 5 个日志级别测试全部通过
- **没有下载任何 JDK**（说明 JDK 25 那个要求已经彻底解决）

**如果失败**：把完整输出留档。失败本身就是有价值的结论——它决定了"跨平台结构能不能在这个工具链版本上成立"，不行的话要立刻决定是换插件写法还是降工具链版本。

**产出物**：构建日志存到 `docs/records/01-构建验证.md`。

### 任务 1.2 建 Git 仓库（0.5 天）

**做什么**：`git init`，加上 `.gitignore`（`.gradle-home/`、`.analysis/` 已经加好了），提交第一版。

**为什么**：现在整个项目**没有版本管理**。第一章的所有实验、三周的验证记录，都需要能追溯。

**怎么算通过**：`git log` 能看到提交；`git status` 是干净的。

### 任务 1.3 支持矩阵草案（1 天）

**做什么**：写清楚这个库支持哪些版本，一张表。

**必须包含**：最低支持的 Kotlin、AGP、Gradle、安卓版本，以及（将来）苹果开发工具版本。

**现在的参考值**（从项目实际状态读出来的，不是猜的）：

| 项 | 当前值 | 说明 |
|---|---|---|
| Gradle | 9.5 | 项目实际用的 |
| AGP | 9.3.0 | 项目实际用的（TRouter 是 9.3.2） |

**要顺带决定的一件事**：我们对外说"最低支持 Kotlin 几"？**建议先跟项目自己用的一致（2.2.10）**，等真有人用再谈放宽。

**产出物**：`docs/records/03-支持矩阵.md`。

### 任务 1.4 单模块 App 能不能无痛接入（1 天）

**做什么**：写一个最小的示范——极简到只有 `logcat` 输出，放在 `app` 模块里，确认**一个只有单个模块的普通 App，接入时不需要理解"组件""模块"这类概念**。

**为什么**：这是约束 18 的验收方式。外部用户大多数没有组件化架构，如果接入第一步就要他们注册"来源身份"，人就被劝退了。

**怎么算通过**：接入代码里**没有出现"组件""模块""来源注册"这类必须理解的概念**，也能跑起来打出日志。

**产出物**：一段在 `app` 里的示范 + 记录"接入需要几步、每步要理解什么"。

## 第 2 周：标签方案实测（最值钱的一周）

**这是整个第一阶段最重要的一件事。**

### 任务 2.1 三种方案各做一个小样（3 天）

**背景**：系统日志的标签有长度限制，而"标签里要不要塞来源、链路、会话"直接决定**你每天看日志顺不顺**。这个决定不能靠讨论，只能靠眼睛看。

三种方案：

| 方案 | 标签长什么样 | 上下文（链路/会话）放哪 |
|---|---|---|
| **A** | `Net/OkHttp` | 不放 |
| **B** | `Net/OkHttp` | 放在正文开头做前缀，比如 `[a3f9] ...` |
| **C** | `Net/OkHttp` | 只做结构化字段，正文和标签都不显示 |

**做什么**：同一个业务场景（模拟一次"下单"，跨界面、业务、网络三个来源，打 5 条日志）三种方案各打一遍。

**注意**：小样代码写完就可以扔，不要花时间做质量。

### 任务 2.2 在真机日志窗口里对比（1 天）

**怎么比**（在安卓 Studio 的日志窗口里逐项看）：

| 看什么 | 怎么算好 |
|---|---|
| 一屏能放下多少条 | 方案 A/B 应该差不多；如果 B 的前缀太长导致换行，就是减分 |
| 按来源过滤 | 点一下标签就能只看"网络"，三个方案都要做到 |
| **按链路过滤** | 这是关键：方案 B 靠关键字能过滤；**方案 C 很可能根本过滤不了**——因为日志窗口不认识你的结构化字段 |
| 视觉噪音 | 前缀是否让人看正文更累 |

**我预判的结论（要靠实测确认）**：**方案 C 在第一版的日志窗口里是"看不见"的**——上下文进了结构化字段但窗口不认识，等于白记。所以第一版要么用 B 过渡，要么给 C 配一个自己的查看方式（那是第二版的事）。

**如果实测确认了这一点，就是本阶段最有价值的发现**：它意味着"标签里必须有足够信息"这条约束是真的，后面所有格式化设计都按这个来。

**产出物**：三种方案的截图（同一个场景）+ 一张对比表 + 结论。

### 任务 2.3 把结论写进设计（1 天）

**做什么**：按实测结果定下标签格式，并写出**为什么排除另外两个**。

**产出物**：`docs/records/05-标签方案决策.md`（含截图和三选一的理由）。

## 第 3 周：接口标准初稿

### 任务 3.1 定接口的形状（2 天）

**做什么**：写一版**对外接口的初稿**（先写文档，不写实现）。必须想清楚这几件事：

| 要定的 | 为什么要现在定 |
|---|---|
| 怎么打日志（函数长什么样、消息是否惰性求值） | 惰性求值是性能的一半答案，且改起来影响所有调用点 |
| 怎么声明"来源" | 约束 18：必须可选、用户自定义名字 |
| 怎么设置级别（来源级 + 全局覆盖） | 两级开关是组件化架构的刚需 |
| 上下文怎么带（链路号、会话号） | 约束：开发者只在入口标一次 |
| 没初始化时的行为 | 约束 19：不许崩 |
| 出错怎么让用户知道 | 约束 19：不许静默吞 |

**为什么要写文档而不是直接写代码**：因为**对外用户意味着接口一旦发出去就基本改不动**。写文档改起来便宜，写代码改起来贵。

**怎么算通过**：一个不认识这个项目的人读完这份文档，能说出"我要怎么用它"，并且能指出哪些地方他没看懂。

### 任务 3.2 定死"不变量"（1 天）

**做什么**：从 `docs/架构设计约束-日志组件.md` 附录里挑出**第一版就要守**的那批（第 8 章有分批表），逐条确认：这条在第一版真的守得住吗？守不住就现在改范围。

**产出物**：`docs/records/07-第一版不变量.md`（只列第一版要守的，加一句"怎么验收"）。

### 任务 3.3 目录与包结构定稿（1 天）

**做什么**：按模块划分表，确认第一版**实际要建哪几个包**（不要把所有分支目录都预建空模块）。

**建议**：第一版先放在 `TLogger` 一个模块里，用包名区分（`com.tlogger`、`com.tlogger.output`…），**等真正需要单独发布某个部分时再拆模块**。

### 任务 3.4 支持矩阵过一遍 PR 式自检（1 天）

**做什么**：拿第 1 周的支持矩阵，对着接口初稿过一遍："这个接口在最低支持的版本上能用吗"。

## 第 4 周：外部用户验证（决定成败的一周）

**这一步很土，但它决定后面半年会不会白干。**

### 任务 4.1 找 2 到 3 个人（2 天）

**找谁**：不认识你、但写过安卓的人（同事以外的最好）。技术群、开源项目的 issue 区、朋友的朋友都行。

**怎么聊**（30 分钟，按顺序）：

| 顺序 | 做什么 / 问什么 | 想验证什么 |
|---|---|---|
| 1 | 让他**演示他现在怎么找日志**（用他自己的项目或随便一个 Demo） | 真实工作流，而不是他嘴上说的 |
| 2 | 问："有没有遇到过日志散在各处、串不起来的情况？" | 痛点是真是假 |
| 3 | 给他看我们的小样：**能不能一眼看出这是哪个来源打的、这次操作串起来了** | "找得到、串得起来"对他有没有价值 |
| 4 | 问："如果一行依赖就能接进来，你会试吗？为什么？" | 装不装的真实门槛 |
| 5 | 问："什么样的日志库你会装？什么会让你不装？" | 反向需求 |
| 6 | 问："你愿意为日志改多少代码？" | 迁移成本的底线 |
| 7 | 问："如果它还能自动把手机号身份证打码，这对你有意义吗？" | 打码是不是真需求（我们的第一楔子） |

**注意**：第 1 步和第 2 步**不要给他看我们的东西**——先看他的真实做法，再看我们的。顺序反了就只能听到客气话。

### 任务 4.2 记录与结论（1 天）

**必须记的**：每个人每句话的原话要点，尤其是**反对意见**。

**产出物**：`docs/records/09-外部用户验证.md`。

### 任务 4.3 Go / No-Go 判断（1 天）

四周结束，基于证据做判断。**这是本阶段的正式交付**。

| 结论 | 触发条件 | 下一步 |
|---|---|---|
| **Go（按计划）** | 至少 2 人说"会试"，且至少 1 人在演示中表现出"串不起来"的痛 | 进第二阶段（输出端地基） |
| **转向：只做打码** | 大家对"找日志"没感觉，但对隐私打码反应强烈 | 第一版砍成"打码 + 编译期检查"，3 个月出货 |
| **降级：先自用** | 没人有兴趣，但你自己确实需要 | 只按自己的需求做，不追外部采用，范围砍到最小 |
| **No-Go** | 技术前提不成立（比如跨平台结构建不起来）且没有替代方案 | 停下，写清原因 |

**产出物**：`docs/records/10-第一阶段结论.md`（含证据、结论、下一步）。
