# TLogger 日志库 · 可行性分析报告（通俗版）

> 这份文档用大白话写成。凡是躲不掉的专业词，第一次出现就当场解释。
> 技术细节的原始版留在 `docs/feasibility-and-architecture-report.md`，那份是给以后写代码时查的，你不用看。
>
> 当前状态：还没开工，只有个空项目壳子。
> 项目壳子的实际情况：安卓构建工具是最新的（Gradle 9.5、AGP 9.3、Kotlin 2.2.10），安卓版本要求是 24 以上（不是文档里写的 21），另外**还没建 Git 仓库**。

---

## 一句话结论

**能做，而且第一版就能做成你每天都会用的东西——但前提是把顺序改过来。**

原来我们把"往硬盘写日志"当成主角。那是**线上回捞**才会用到的能力；而你（以及绝大多数外部用户）每天真正在用的，是**看日志**这一端。

所以第一版的重点是：

**一条能每天用的链路（输出 + 找得到 + 串得起来）+ 自动打码 + 写代码时的隐私检查。**

落盘、公开格式、独立解码工具这些是"无锁定"的核心，但它们是**第二版**的事——只有线上回捞才需要。

这样第一版大约 **6 到 8 个月**，而且**全程纯 Kotlin，不碰底层、不碰多平台打包矩阵，风险比原来小一个量级**；做完的那一天你就在用它。

## 第一章 这东西能不能做

### 1.1 先说清楚我们在做什么

做一个"程序写日记"的工具箱。程序出问题时，靠它记录下来的日记查案。

你的四个卖点，翻译成人话：

| 卖点 | 人话解释 | 打个比方 |
|---|---|---|
| 高性能持久化 | 写日记不能拖慢程序本身，而且要真的存到硬盘上 | 别人是"写好纸条→交给管家→管家开抽屉放好"；我们想让日记本直接摊在桌上写 |
| 跨平台（KMP） | 安卓、苹果、电脑服务器上，同一套接口，写一遍到处能用 | 一个充电器配三种插头 |
| 隐私合规 | 手机号、身份证、邮箱在写进日记之前自动涂黑 | 门口的保安，看见敏感东西先打码再放行 |
| 不上锁 | 日记格式公开，给你一个小工具，谁的电脑都能打开看 | 反面例子是美团 Logan：想看懂日志，你得先把他家服务器搭起来——这就是"上了锁" |

### 1.2 四个卖点能塞进一个东西里吗？能，但有一处真打架

我一条一条配对比过，结论是：

- **基本不冲突**：跨平台、打码、不上锁、写得快，这四样互相之间不打架。
- **有一处会互相牵制**：写得快和"全自动打码"会互相拉后腿。因为打码意味着**每一条日记都要先检查一遍**，检查是要花时间的。解法是把打码分三层做：能提前标记的字段，在日记还没成形的时候就处理掉；实在没法预判的自由文字，再在落盘前扫一遍；扫描前先用便宜的办法筛一遍（看长度、看格式像不像），别一上来就做复杂判断。
- **有一处是真打架，只能靠取舍**：**加密** 和 **不上锁**。

### 1.3 唯一真打架的地方：加密和"不上锁"

这俩天生矛盾。要上锁就得有钥匙，那钥匙放哪？只有三种可能：

| 钥匙放哪 | 会发生什么 | 能不能接受 |
|---|---|---|
| 焊在 App 里 | 别人把 App 拆开就能拿到钥匙。这叫"心理安慰锁"。我们还必须跟着一起假装很安全，一旦被人拆穿，做开源的最怕这个——名声就毁了 | 不能 |
| 放我们服务器上 | 用户想看懂日志，必须先连我们的服务器。**这就变成美团那种模式了**，跟"不上锁"的承诺自己打自己脸 | 不能 |
| 用户自己手里（比如他自己设的密码） | 这是唯一说得通的 | 可以，但安全能力有限 |

所以第一版我的建议是：**不做加密，但格式里先把位置留出来**，以后想加不用推倒重来。同时老老实实写清楚"我们能防什么、防不了什么"，绝不吹牛。

### 1.4 为什么不建议一次全做完

**不是技术上做不到，是养不起。**

打个比方：四道招牌菜都能上菜单，但只有你一个人当厨师。

麻烦不在"做菜"，在**维护**——手机系统、开发工具每年升级好几次，每次升级你这个工具都可能坏掉，你得跟着修。光"跟着修"这一项，保守估计一个月要搭进去一到两天。再加上回复别人提的问题、发新版本、改文档，一个月又是两三天。

**结果是：一个月不发新版本，别人就开始怀疑你还做不做；三个月不发，基本就被当成"弃坑"了。**（腾讯的 XLog 就是这么被淘汰的，我们要避免变成下一个 XLog。）

还有一个很实际的负担：这个库要同时支持安卓、苹果、电脑，每支持一个平台就要多打几份不同的包。全部算下来大概要维护 **15 到 20 份不同版本的文件**，每发一次新版本都得全部重新打一遍、全部验证一遍。

**一个特别有效的减负招**：电脑和服务器上**不要**塞那套底层加速的东西，直接用 Kotlin 写一版普通版就行。电脑上快一点慢一点没人计较，但这样能省掉为 Windows、Mac、Linux 分别打包的**六份文件**，负担直接砍掉一大半。

### 1.5 开工后容易撞上的坑（提前知道，省得撞上）

这些是我查资料时觉得"调研阶段最容易漏、开工后最疼"的地方。

**坑一：硬盘写满的时候，程序会直接崩掉。**
用"日记本直接摊在桌上写"这个手法有个副作用：如果桌上没地方了，系统不是给你报个错，而是**直接把你的程序干掉**。著名数据库 LevelDB 就出过这个问题。
怎么办：提前把位置占好，写之前检查还剩多少地方，快满了就换新文件。

**坑二：安卓新手机换了"内存分页"的新规矩（每页从 4KB 变成 16KB）。**
如果底层代码里把"每页 4KB"写死了，结果就是**老手机上一切正常，新手机上一启动就崩**——这种问题极其难查。
怎么办：不写死，每次运行时去问系统。另外构建工具要用新版本，打包时自动检查一遍。

**坑三：iPhone 锁屏之后，日志文件会被系统锁住。**
苹果出于安全，默认让文件在锁屏后不可读，这时候写日志会直接失败。
怎么办：主动把文件的安全级别调低一档（这是一个要写进文档的取舍），另外还要注意 iPhone 会在后台悄悄杀掉你的程序，得在被杀之前把数据存好。

**坑四：Kotlin 连接底层代码这条路，官方自己说还在"试用期"。**
官方文档明确写着：这个功能目前是**测试状态**，理由就是"可能影响你的代码跟不同版本的 Kotlin、不同版本的开发工具之间的兼容性"。
具体会遇到的麻烦：每个 Kotlin 版本只跟某一个特定版本的苹果开发工具配合得最好，苹果工具升级了可能直接编不过；底层库里带的东西会被强制塞给所有用户，可能跟别人的东西撞名。
怎么办：**接口定得越简单越好，只用最基础的 C 语言接口**，不要用那个更花哨但更不稳定的 C++ 接口。这一条非常重要，因为它同时决定了"选 C++ 还是选 Rust"。

**坑五：调试底层崩溃很费时间。**
底层代码崩了，报出来的是一堆看不懂的地址。得提前把"翻译成人话"的流程建好（安卓叫符号化，苹果叫 dSYM），不然第一次线上崩溃就能耗掉你好几天。

**坑六：发到公共软件仓库这一步，比想象的麻烦。**
安卓/Java 世界的"应用商店"叫 Maven Central。想发上去要签名、要附带源代码文档、还要处理"同一个库有好几个平台版本"这种麻烦事。
顺便说个好消息：我查过了，**腾讯 XLog 和美团的 Logan 都没有发到这个公共仓库上**（我直接去仓库目录查了，找不到）。这对我们是机会——同时也说明这一步是这类库常见的死穴。
另外提醒：老的发布通道已经停用了，现在必须走新的通道，这一步要提前确认好。

**坑七：Kotlin 版本对不上。**
项目壳子里用的是 Kotlin 2.2.10，而官方现在最新是 2.4.20。这事必须在开工第一个月定死：我们最低支持到哪个版本、推荐用哪个版本，写清楚公开出去。不然"我这边编不过"会成为最高频的求助。

**坑八：项目还没建 Git 仓库。**
这不算技术坑，但第一步就得补上，不然连代码版本管理都没有。

### 1.6 这一章的结论

| 问题 | 结论 |
|---|---|
| 四个卖点能一起做吗 | 能。唯一真打架的是"加密 vs 不上锁"，只能靠产品上的取舍解决 |
| 技术上危险吗 | 中等。危险主要来自"底层代码崩了很麻烦"和"Kotlin 连接底层这条路官方还在测试期" |
| 工程上危险吗 | **高**。真正的风险是"范围太大 + 要维护的东西太多 + 只有你一个人"，这比任何技术问题都更可能让项目黄掉 |
| 什么情况下干脆别做 | 如果你只是想让"自己 App 里日志好用一点"，那用现成的（XLog、Glog、MXLogger）就够了。自研真正值得做的理由只有一个：你要的这几样东西（自动打码 + 格式公开 + 多平台一套）现成的确实没凑齐，而且是你长期要用的 |
| 建议 | 分阶段做，而且**顺序要倒过来**：第一版做输出链路 + 打码 + 检查（纯 Kotlin，日常就能用），落盘和公开格式放第二版。理由见第四章 |

## 第二章 先把市场调研里的几处改对

大方向是对的，但有三处偏差会直接影响"先做什么"的判断，必须先改过来。

### 2.1 有一处数字看错了

那份滑铁卢大学 2025 年的研究（分析了 48,702 个安卓 App），原文的意思是：

- **49.3% 是"用了日志工具的 App 里，有一半存在泄漏"**——不是"泄漏里有一半是用户信息"。
- 泄漏的源头里，**用户信息占 69.7%**，用户手动输入的内容占 30.3%。

这个更正**对我们反而是好消息**：说明"用户信息字段"是最大的泄漏来源，而我们打算做的"给字段打标记、自动打码"正好治这个。

### 2.2 最重要的一句话：只有 3.4% 的 App 用了第三方日志工具

同一个研究里的另一个数字，我认为比上面那个更重要：

**在四万八千多个 App 里，用了第三方日志工具的只有 3.4%。也就是说一百个 App 里只有三个半。**

这句话决定了三件事：

1. **别指望"我做个更好的日志库，大家就会来用"。** 不是你的东西不好，是大家根本不愿意为日志换工具——换工具要改代码、要重新测，太麻烦。
2. **项目的成功标准不能定成"多少人 star"。** 应该定成"我自己项目真的在用它"。
3. **进攻方向要变**：不是"做个更好的日志库"，而是"**让那 96.6% 不用日志库的人也能减少泄漏**"。这才是真正的空子。

### 2.3 还有一个更关键的发现：光靠运行时打码不够

研究说，**62.5% 的泄漏不是"直接写了手机号"，而是数据传了几手之后才被写进日志的**（路径大概 2 到 4 句话）。

这种泄漏，程序运行时是抓不到的——因为等它看到的时候，字符串早就拼好了，它不知道里面那个数字原来是什么。

**只有在"写代码的时候"用检查工具才能揪出来。**

所以正确做法是两手都要抓：

- **写代码时**：用检查工具（安卓上叫 Lint）提醒"你这行代码可能把敏感数据写进日志了"
- **运行时**：真写下去之前自动打码当兜底

这条是我对原调研最重要的补充。

### 2.4 五个"市场空白"重新排价值

| 调研里的空白 | 真的是痛点吗 | 能当卖点吗 | 我的建议 |
|---|---|---|---|
| 一、自动打码 | **是**，而且有数据支撑 | **能**，而且唯一能做到"用户不用改代码就能用" | **第一优先** |
| 二、不上锁的高性能日志 | 是（选型时确实会担心） | 能，但真正的门槛是"公开的格式说明 + 测试"，不是代码 | 和底层一起做 |
| 三、跨平台 + 高性能 | 弱（需要它的人本来就少，而且这些团队多数已经用 Sentry 之类的了） | 是交付方式，不是购买理由 | 能做到就行，别当宣传主轴 |
| 四、和监控平台对接 | 一般（趋势是真的，但那套标准自己还在变） | 算半个（别人已经有类似能力了） | 放到第二版 |
| 五、用 ZSTD 压缩 | 低 | **不能** | 只是个实现选择，挂出去会被人笑话 |

**展开说一下第五点为什么不算卖点**：ZSTD 只是一种压缩文件的方法，把旧的 zlib 换成它，是一小时的活，谁都能抄。拿它当招牌是撑不住的。

### 2.5 名字别撞车

"Glog"这个名字已经被两个不相关的项目占了（谷歌的和货拉拉的），说明这条路很挤。另外"Logger"这种词也太通用。

建议：正式定名前，去公共软件仓库、GitHub 和商标库都搜一遍。"TLogger"也要搜。

## 第三章 架构怎么选

> **先说明这一章的位置**：整章讨论的是**"往硬盘写日志的那个引擎"**（C++ / Rust / 纯 Kotlin 怎么选）。
>
> 按现在的路线，**第一版根本不涉及这个选择**——第一版是输出链路，纯 Kotlin，不碰底层。
>
> 所以这一章的内容**整体挪到第二版再用**。但里面有一条现在就要执行：**先把"接口标准"和"格式规范"定死**，这样第二版做引擎时才有得选、才有得退。

### 3.1 先搞明白一件事：真正要定死的不是"用什么语言"

大多数人一上来就纠结"底层用 C++ 还是 Rust"，这是个陷阱。

**真正要先定死的是两样东西：**

1. **接口标准**——就像插座，上面和下面约定好用哪几个口对接、怎么对接。
2. **日记文件的格式**——公开写清楚，第几个字节是什么、代表什么。

只要这两样定死了，底层用什么语言写，就像**换个插头**一样，随时能换。

这个想法的最大价值是保险：**万一以后发现底层这条路走不通，可以退回到纯 Kotlin 版本，不用把整个项目推翻。**

### 3.2 四种做法

**做法一：Kotlin 外壳 + C++ 内核**

- 好处：团队熟悉（做安卓的人大多见过 C++），现成的压缩、加密库拿来就用。
- 坏处：C++ 写错了就是直接崩，全靠人的自觉。而且它有个很大的诱惑——**那个官方还在测试期的 C++ 接口看起来更好用**，很容易顺手用上，然后整个库就被绑在一个不稳定的东西上。
- 适合：团队本来就有 C++ 积累。

**做法二：Kotlin 外壳 + Rust 内核**

- 好处：Rust 这门语言会强制你只能走最基础、最稳定的那条接口路（就是前面说的 C 语言接口），**等于从机制上防止你踩坑**。它还有一整套现成的工具帮你自动找错、自动跑大量随机测试。
- 坏处：要学。另外底层库的体积需要专门调小。
- 适合：没有现成 C++ 积累的团队。

这里有一条反直觉的判断：**在做苹果版本这件事上，Rust 其实比 C++ 更安全**。因为 C++ 那条路是"看起来方便、实际不牢靠"，Rust 是被迫走那条稳的路。

**做法三：纯 Kotlin，不要底层**

- 好处：最省事。不用配一堆构建工具，没有底层崩溃的风险，调试舒服，开发速度快四成以上。
- 坏处：**速度上不去**。而且真正拖慢速度的地方还不是"存文件"，是"把日志内容拼成一句话"这一步——这一步在 Kotlin 里省不掉。所以如果选它，"性能对标 XLog"这种话就不能说了。
- 适合：如果把"合规和可验证"当第一卖点，这其实是**性价比最高**的做法。

**做法四（我推荐的）：分开对待**

不是三选一，而是上面几种做法同时用，按平台分工：

| 平台 | 用什么 | 为什么 |
|---|---|---|
| 安卓 | 底层内核 | 性能主战场，而且只需要打 3 到 4 份包 |
| 苹果 | 同一套底层内核 | 跟安卓共用，省一半功夫 |
| 电脑 / 服务器 | **纯 Kotlin 版** | 直接省掉六份包的维护工作，性能损失无所谓 |
| 测试用 | 一个"假装写文件"的版本 | 用来故意制造各种故障，看它崩不崩 |

**做法四真正的好处是"可以退货"**：如果开工一个月后发现底层这条路问题太多，可以退回到做法三，不用推倒重来。

### 3.3 四种做法摆在一起比

| 比什么 | 做法一 C++ | 做法二 Rust | 做法三 纯 Kotlin | **做法四（推荐）** |
|---|---|---|---|---|
| 做砸的风险 | 中高 | 中 | 低 | 中（能退回低风险路线） |
| 速度上限 | 最快 | 最快 | 中等 | 手机上最快，电脑上中等 |
| 好不好维护 | 中（靠自觉） | 好 | 好 | 好 |
| 要配多少构建工具 | 多 | 中 | 少 | 中 |
| 会不会被"测试期功能"坑 | **容易** | 不容易 | 不会 | 不容易 |
| 找人接手容易吗 | 容易 | 一般 | 最容易 | 一般 |
| 出内存错误的风险 | 高 | 低 | 低 | 低 |
| 多久能出第一版 | 中 | 慢 | **快** | 中 |

### 3.4 几个具体的小块该放在哪一层

| 这块功能 | 放在哪 | 人话理由 |
|---|---|---|
| 写文件的手法 | 底层内核 | 只有底层才碰得到硬盘 |
| 压缩 | 底层内核，后台线程做 | 压缩费时间，不能让主线程等着；重要日志可以先不压缩直接落盘，图个"立刻就在硬盘上" |
| 加密 | 第一版不做，只留位置 | 见 1.3 |
| 给字段打码 | 上面一层，**在内容还没变成日记之前就处理掉** | 这样敏感内容根本不会进到后面的环节，比"写完了再擦"安全得多 |
| 给自由文字扫敏感词 | 底层，落盘之前 | 这里能看到最终文本，是最后一道闸 |
| 检查规则本身 | 上面一层（共用代码） | 一套规则三个平台都能用 |
| 时间戳 | 上面一层采集，底层记录 | 要同时记"精确的流逝时间"和"墙上时钟"，两个都要，不然时间会乱 |
| 崩溃时数据的处理 | 底层 | 这是底层独有的能力 |

### 3.5 日记文件该长什么样

先说结论：**外层自己定一套简单规矩，里面装的内容用一种通用的表格格式，对外还能导出成人能直接读的版本。**

候选的三种"记表格"写法，用人话比较：

| 写法 | 好处 | 在我们的场景里合适吗 |
|---|---|---|
| FlatBuffers | 读的时候不用解析，直接就能取到某一项 | **不合适**。它是为"随便跳着读"设计的，而我们是"一直往后追加、从头往后读"，这个好处用不上，却要多背一套工具。MXLogger 用它是因为它要给 Flutter 传数据，跟我们目标不一样 |
| Protobuf（推荐） | 以后想加字段很容易，体积小，工具齐全，跟主流监控平台天生能对上 | **最合适** |
| CBOR / MessagePack | 不用提前定义结构 | 备选，纪律性差一些 |
| 自己完全定制 | 最快 | 只用在最外层那圈"包装纸"上，不用在内容上 |
| JSON | 人能直接读 | 作为**导出格式**，不作为存储格式 |

补充一条反直觉的判断：**第一版不要做"索引"**（索引 = 为了快速查找而额外建的表）。
因为文件按天或按大小切开之后，每个文件都不大，从头扫一遍根本不慢。真要"看崩溃前 10 秒发生了什么"，第二版在文件末尾加一小块摘要就够了，不需要搞成搜索引擎那套。（而且原调研明确说了"不做全文检索"。）

### 3.6 查看日志的工具用什么做

| 形态 | 成本 | 值不值 | 建议 |
|---|---|---|---|
| 一份公开的格式说明 + 几个样本文件 | 很低（一周） | **最值**，这是"不上锁"真正的载体 | **第一版必做** |
| 官方解码工具（跟底层同一门语言，跟着库一起发） | 低 | 测试和工具共用一套，不会两个版本对不上 | **第一版必做** |
| 命令行工具（双击就能用，不用装环境） | 中（两三周） | 开发和运维直接能用 | **第一版必做** |
| **用 Python 再独立写一个解码器** | 中（一到两周） | **这是"不上锁"最有力的证据**：如果必须看你的源码才能解码，说明你的格式说明写得不够清楚 | **强烈建议第一版做** |
| 图形界面 | 高（四到六周） | 体验好，但第一版的用户其实只有你自己 | 第二版再说 |

关于图形界面：以后要做的话，推荐用 Compose Desktop（复用你现有的 Kotlin 技能）或者 Tauri（复用 Rust 内核）。

### 3.7 跟监控平台怎么对接

现在流行把这些日志接到监控平台上统一看。我们的建议是分三步走，第一版只做第一步：

1. **只做"翻译"**（第一版）：把我们的日志内容翻译成监控平台认识的格式，并提供几个接口让调用方自己接。**不依赖对方的库**。
2. **提供现成的对接插件**（第二版）：而且要单独一个包，谁想用谁装。**绝对不能塞进主库里**，不然所有人都会被迫背上体积变大和版本冲突的麻烦。
3. 完整的自动对接：超出日志库该管的事，不做。

## 第四章 先做什么、后做什么

### 4.1 重新排优先级（按"每天会不会用到"）

打分逻辑：每天会用吗、用起来麻烦不麻烦、做起来贵不贵、别人好不好抄。

| 候选 | 每天会用吗 | 换起来麻烦吗（越低越好） | 做起来贵吗（越低越好） | 别人好不好抄（越高越好） | 排在哪 |
|---|---|---|---|---|---|
| **输出端**（找得到 + 模块维度 + 短标签） | **每天** | 麻烦（但可用"对接件"绕开） | 一般 | 一般 | **第一版**（地基 + 日常价值） |
| **自动打码 + 写代码时检查** | 每天（隐式生效） | **一点都不麻烦** | 一般 | 一般 | **第一版**（唯一的零迁移楔子） |
| **链路串联 + 会话上下文** | 每天 | — | 偏贵 | 一般 | **第一版**（最痛的那件事） |
| **最近 N 条环形缓冲** | 经常 | — | 便宜 | 容易 | **第一版**（通往落盘端的接缝） |
| 落盘 + 公开格式 + 独立解码 | 出线上问题时 | 很麻烦 | **很贵** | **很难抄** | **第二版**（无锁定的核心，但日常用不到） |
| 跨平台一套 | 一般 | 一般 | 贵 | 容易 | 安卓先行，苹果跟上 |
| 加密 | 偶尔 | 一般 | 贵 | 容易 | 第二版之后 |
| 用 ZSTD 压缩 | 不会 | 不麻烦 | 很便宜 | 极容易抄 | 忽略（这只是个实现细节） |

**这张表跟原来最大的区别**：原来"写得快的底层"排在"必须做"，现在它整体挪到了第二版。不是因为它不重要——**"无锁定"是我们的护城河，但它服务的是"线上回捞"这个一年用几次的场景**，而输出端服务的是每天。先把每天用的做好。

### 4.2 陌生用户凭什么装你的库？只有两个理由

你确认了日志的第一使用者是**外部用户**（陌生人）。这一条把整个判断的松紧都改了。

一个陌生人愿意装一个库，只可能是因为两件事之一：

1. **它解决了你每天都会遇到的痛** → 这是**输出端**负责的（找得到、串得起来）
2. **它解决了一件你害怕的事** → 这是**打码 + 写代码时检查**负责的（隐私泄漏）

**注意这两条里都没有"性能更好"。** 性能是加分项，不是装机理由——对绝大多数 App 来说，系统自带日志已经"够快"了（这也解释了为什么一百个 App 只有 3.4 个装第三方日志库）。

所以第一版里的三件事各有分工：

| 谁 | 负责什么 | 用户要改代码吗 |
|---|---|---|
| **自动打码** | 让人**愿意试**（装上就生效，一行都不用改） | 不改 |
| **输出端** | 让人**留下来**（每天用，用了就回不去） | 要改，但可以用"对接件"绕开 |
| **写代码时检查** | 让人**不敢不用**（合规压力，而且真能查出问题） | 加个构建配置就行 |

**打码依然是那个唯一的"零迁移楔子"**——它是陌生人认识你的入口。但光有入口不够：**入口把人带进来之后，是输出端决定他留不留下。**

**同时要诚实面对一个代价**：第一版不包含落盘，所以"性能很强""无供应商锁定"这两个说法都要往后放。**在第二版做完、并且有公开测速数据之前，不许对外提性能。**

### 4.3 第一版做什么、不做什么

**第一版（对外首发）一定要做：**

1. **统一接口 + 模块维度**：日志带上"出身"信息，能按维度归类、过滤。**维度名由用户自己定义**，不写死成我们这套架构的概念——外部用户大多数只有一个模块，硬塞"组件"概念会把人劝退
2. **两级开关**：每个来源自己声明默认级别，上层能统一覆盖，互相不打架
3. **输出端**：统一格式、长日志自动拆分不丢内容、惰性求值、没初始化也不崩
4. **链路串联 + 会话上下文**：一次业务操作的日志能串成一条（跨协程和线程自动传递）；日志自动带版本号、会话号、账号（打码后）
5. **最近 N 条的环形缓冲**：撑不过进程被杀，但能回答"刚才发生了什么"；**它是通往第二版落盘的天然接缝**
6. **打码的一整套**：字段标记、自由文本识别、换代号、写代码时的检查、能单独发出去的打码小工具
7. **对接件**：Timber / SLF4J / Kermit / 苹果的 swift-log——用户不换工具也能接进来
8. **发布与文档**：发到公共仓库、支持矩阵写清楚、明确说清"第一版不做什么"

**第二版（V2）做——"无锁定"的核心：**

落盘引擎（内存映射）+ 公开格式规范 + 独立解码器 + Python 二次实现 + 命令行工具 + 苹果落盘 + 可复现测速。
（验收标准见 `docs/架构设计约束-日志组件.md` 里的 19 条约束。）

**第一版明确不做：**

- **落盘**（整体挪到第二版，理由是日常用不到）
- 加密（只留字段位置 + 写清威胁模型）
- 监控平台对接
- 图形界面、日志时间线视图
- 上传到云端的平台、实时日志流、全文搜索、崩溃收集（那是 Sentry 的活）
- Flutter 版本、网页版、Windows/Mac/Linux 的底层加速版
- **XCFramework / SPM / CocoaPods**（第一版只服务 Kotlin 跨平台项目）
- **编译器插件**（先用编译期检查工具达到九成效果）

### 4.4 第一版的六个阶段

#### 第一阶段：定方向 + 打个小样看看"到底有没有人要"（4 周）

**要做出什么：**

1. **接口标准的初稿**，以及"以后不许随便改"的规矩（对外用户意味着接口一旦发出去就基本改不动了，见第 7 章第 14 件）
2. **标签方案的实测**：把三种标签方案各做一个小样，摆在同一块真机日志窗口里比谁更好读。**这是输出端最难的设计决策，必须亲眼看，不能靠讨论。**
3. **外部用户视角的验证**：找 2 到 3 个不认识你的安卓开发者，把你现在"看日志"的整个流程演示给他们看，直接问"你会装吗？为什么？"——**这一步很土，但能省掉半年白干。**
4. 自动构建骨架 + 支持矩阵草案 + **把 Git 仓库建起来**（现在还没有）
5. 顺手确认一件事：**AGP 9 上那个新版跨平台安卓插件能不能用**（kmp-logcat 用的是旧一代的组合，我们得在 AGP 9 上重走一遍）

**怎么算合格：**

- 三种标签方案里能明确选出一个，并且能说出为什么
- 至少 2 个外部开发者表示"愿意试用"（哪怕是嘴上说说）
- 一个空工程，两分钟内跑起来，打出一条带来源维度和会话号的日志

#### 第二阶段：输出端地基（6 到 8 周）← **做完这一阶段，你每天就能用**

**要做出什么**：统一接口 + 来源维度（**维度名由用户自己定义**）+ 两级开关 + 安卓输出通道 + 长日志自动拆分 + 惰性求值 + 统一格式 + 没初始化不崩。

**怎么算合格：**

- 一个开关能"只看某个来源"的日志
- 两个来源各自的级别互不干扰，而且上层能一句话全部覆盖
- 打一条 10KB 的长日志，窗口里能完整看到（分段能拼回来）
- 循环里打十万条日志不卡（拼字符串的代价被"惰性求值"挡掉）
- 第三方 SDK 的日志能被一键屏蔽
- **你自己的项目切过来，一天之内完成，并且当天就不想再改回去**

#### 第三阶段：打码 + 写代码时的检查（5 到 6 周，可以和第二阶段并行）

**要做出什么**：给字段打标记的接口、敏感内容识别规则（邮箱、手机号、身份证、银行卡、IP、网址里的密码、登录凭证、经纬度）、把内容换成代号的机制（同一个手机号每次换成同一个代号，能对上号但看不出是谁）、写代码时的检查规则、能单独发出去的打码小工具、**一批公开的测试素材**。

**怎么算合格：**

- 在公开素材上（至少 2000 条）：**该抓的抓到 99% 以上，抓错的不超过 5%**
- 对速度的影响不超过 5%
- 误伤率（正常日志被误改）不超过 2%，而且每次改动都能在报告里查到
- 写代码时的检查工具，在自研项目 + 3 个开源 App 上跑：**每个项目误报不超过 10 条**，抓不到的要明确说明
- **打码在开发阶段就生效**（不是只在正式版生效）——测试期最容易把真实用户数据打出来
- **打码小工具在"完全不用我们日志库"的项目里能独立接入**（至少两个示范：接在 Timber 上、接在安卓自带日志上）

#### 第四阶段：链路串联 + 会话上下文 + 环形缓冲（6 到 8 周）

**要做出什么**：一次业务操作的"链路号"能自动跨协程和线程传递；日志自动带上会话号、版本号、账号（打码后）；最近 N 条的环形缓冲；环形缓冲能导出成文本。

**怎么算合格：**

- 一次业务操作打了 5 条日志、跨 3 个来源，**用一次过滤全部出来、顺序正确，而且中间的代码一行都不用改**
- 环形缓冲能存最近 2000 条，内存占用不超过 2MB
- 别人截图给你一条日志，你能看出：哪个版本、哪次启动、哪个账号、哪条链路
- 环形缓冲导出的文本，跟日志窗口里看到的一致

#### 第五阶段：苹果端（6 到 8 周）

**要做出什么**：输出端、打码、链路在苹果上都能用；给苹果官方日志接口做的"对接件"；**只服务 Kotlin 跨平台项目**（不做 XCFramework，理由见第 7 章第 13 件）。

**怎么算合格：**

- 苹果开发者接入，30 行以内写完
- 苹果模拟器和真机各跑通一遍
- **一个"用户视角"的苹果示范工程在自动流程里真的编译链接通过**（不能只编译库本身）

#### 第六阶段：发布与交付（4 到 6 周，可以重叠）

**要做出什么**：发到公共仓库、文档、四种对接件（Timber / SLF4J / Kermit / 苹果的 swift-log）、写代码时的检查能随包自动生效（用户零配置）、支持矩阵、**以及清楚写明"第一版不做什么"**。

**怎么算合格：**

- 全新项目**只写一行依赖就能用**
- 写代码时的检查在用户项目里零配置自动生效
- **找 3 个不是你的人，各自在 30 分钟内完成接入**

#### 之后：第二版（V2）——落盘与"无锁定"

这一版才做原来那份文档里的主角：落盘引擎（内存映射）、公开格式规范、独立解码器、Python 二次实现、命令行工具、苹果落盘、可复现测速。

**它的验收标准就是原来那套**：杀进程不丢、硬盘满不崩、坏点能跳过并报数、独立解码器字节级一致、两个进程同写不打架、改系统时间顺序不乱。

**为什么放到第二版**：这些能力服务的是"线上回捞"这个一年用几次的场景，而第一版服务的是每天。**先把每天的做好，把无锁定留作护城河。**

### 4.5 总共要多久

| 阶段 | 周数 | 在关键路线上吗 |
|---|---|---|
| 一、定方向 + 小样验证 | 4 | ★ 起点 |
| 二、输出端地基 | 6～8 | ★ |
| 三、打码 + 检查 | 5～6 | 可以并行 |
| 四、链路 + 环形缓冲 | 6～8 | ★ |
| 五、苹果端 | 6～8 | ★ |
| 六、发布交付 | 4～6 | 可以重叠 |
| **第一版合计** | **28～37 周** | 一个人投入六到八成精力，约 **6.5 到 8.5 个月** |
| （之后）V2 落盘与无锁定 | 16～22 周 | 约 4 到 5 个月 |

**注意一个变化**：第一版的总时长比原来的方案略长（因为多了输出端这一大块），**但"能每天用"的时间点从第 7 个月提前到了第 3 个月左右**。这个交换是划算的。

**如果你只想尽快验证"有没有人要"**，那第一版可以再砍：**只做输出端地基 + 打码**，大约 3 个月。这也是一条正经路子，但要现在想清楚。

### 4.6 可以停下来的台阶

因为你做的不是"全有或全无"的事：

- **第一级**：输出端地基做完 → **你自己每天就在用了**（这是最重要的一级）
- **第二级**：打码 + 检查做完 → 可以对外发出去，陌生人能零迁移试用
- **第三级**：链路 + 环形缓冲做完 → 第一版的功能完整了，可以正式宣传
- **第四级**：苹果端 + 发布做完 → 第一版对外可用
- **第五级**：V2 落盘做完 → "无锁定"的护城河建成

**每一级都是一个完整能用的东西，不是半成品。做完任何一级都可以停几个月，前面的投入不会白费。**

**而且第一级就是"你自己天天在用"**——这是最强的验证方式：如果做完第二级你自己都不想用，那说明这条路不对，及时止损的成本很低。

## 第五章 会出什么问题

### 5.1 技术上的坑

| 会出什么事 | 概率 | 后果 | 提前看出苗头的信号 | 怎么防 |
|---|---|---|---|---|
| 硬盘满或文件被切，**程序直接崩** | 中 | 严重 | 存储快满的手机上偶发崩溃 | 提前占位置、写前检查剩余空间、快满就换文件 |
| 底层代码写坏内存 | 中 | 严重 | 自动检查工具报警 | 优先选 Rust；只留极小一块危险代码；用机器大量随机输入去撞击 |
| Kotlin 连接底层这条路出问题 | **高** | 一般 | 升级 Kotlin 或苹果工具后编不过 | **只用最基础的接口**；不用那个测试期的接口；公开说明支持哪些版本组合 |
| 要打的包太多，管不过来 | 高 | 较重 | 用户反馈"你这个包在我这用不了" | 电脑上不塞底层；平台范围写死；发布流程自动化 |
| 速度没达到预期 | 中 | 一般 | 实测比预期慢很多 | 别在不需要的时候拼字符串；攒够一批再调底层；先按等级过滤掉不要的日志 |
| 打码拖慢速度、或者误伤正常日志 | 中 | 严重 | 用户干脆把打码关了 | 优先靠"字段标记"而不是猜；扫描前先便宜地筛一遍；规则能关、能看统计 |
| 多个进程同时写打架 | 中 | 一般 | 日志串行、文件损坏 | 一个进程一个文件；不做多个进程共享同一个文件 |
| **时间记录出错**（最容易被忽视） | 中高 | 一般 | 日志时间倒流、跨文件排序乱 | 同时记"精确流逝时间"和"墙上时钟"；把时钟被改动的事件也记下来 |
| 数据悄悄损坏或丢失 | 低 | 严重 | 用户说"日志缺了一段" | 每条记录带校验；读取时能从坏的地方往后跳；**丢掉多少必须报数** |
| iPhone 上锁屏写不进去、被后台杀掉丢数据 | 中 | 较重 | 只在锁屏场景丢日志 | 主动调整文件安全级别；被挂起前先存盘；日志文件排除在备份之外 |
| 新手机（16KB 分页）启动就崩 | 中高 | 一般 | 只在新机型上崩 | 不写死分页大小；用新版构建工具；打包时自动检查 |
| 用户接入时的各种小问题（代码被压缩混淆、找不到底层库） | 中 | 一般 | 用户反馈"提示找不到东西" | 把配置文件随包一起发；**专门做一个"用户视角"的测试工程** |

### 5.2 人的问题（比技术问题更可能让项目黄掉）

| 问题 | 说明 | 怎么应对 |
|---|---|---|
| **用的人少** | 只有 3.4% 的 App 用第三方日志工具，这是天花板 | 成功标准定成"自己项目在用"；做"对接件"让用户不用改代码；打码工具单独分发 |
| **你一个人维护，还要追系统升级** | 光跟着修，一个月要一两天 | 范围砍小；把"追升级"当成固定工作排进计划；每季度发一次维护版；万一真做不动了，**主动公开说"进入维护模式"，别悄悄弃坑** |
| 被别的社区当成"重复造轮子" | 定位说不清就会招来反感 | 说清楚：我们不做日志门面，我们做门面**背后的仓库和合规能力**；主动给 Kermit、Timber 这些项目提对接代码 |
| 别人质疑你的测速数据 | 没有原始数据就站不住 | 公开测速脚本、机型清单、原始数据，**并且主动说明"我们在哪些场景不占优"**——老实是性能宣传唯一可信的方式 |
| 名字撞车 | "Glog"已经被占了两次 | 定名前搜一遍 |
| 别人担心你塞了什么私货在底层库里 | 企业用户会问 | 依赖越少越好；提供清单；发布签名 |
| **你自己没劲了**（最真实的风险） | 没人用的开源项目就是这样慢慢死的 | 第一验收标准是"自己能用"，别人来用算意外收获 |

### 5.3 法律和合规上要注意的

| 事项 | 说人话的情况 | 怎么处理 |
|---|---|---|
| 加密技术出口的法律限制 | 各国对"加密技术"的出口有管制。公开发布的开源软件通常有豁免，但把含加密的程序分发给受限对象仍可能有义务 | 加密默认关闭、单独发；这不是法律意见，真要商业化前找专业的人问 |
| 国内的密码管理法规 | 一个"用了加密的日志工具"通常不属于需要认证的密码产品，但这属于要专业判断的灰区 | 第一版不做加密、不拿加密当卖点；如果以后要做金融政务客户，可以支持国产加密算法（这反而可能成为优势） |
| 隐私法（个人信息保护法、欧盟那套） | **打码是降低风险，不等于"我们就合规了"。** 日志本身可能就算"处理个人信息"（要限制保存时间、要支持删除、要告知用户）。**责任始终在 App 开发者身上，不在我们** | 文档里写清责任边界；提供一键清除旧日志的接口；提供"打码报告"当作一种记录；**宣传语只能用"降低泄漏风险"，绝不能说"通过合规"** |
| 打码会让查问题变难 | 全都涂黑了就没法排障 | 用"换成代号"代替"涂黑"，同一个值永远是同一个代号，能对上号但看不出内容；紧急情况下可以导出对照表（默认关闭，开启时要求加密） |
| 开源许可 | 建议用 Apache-2.0（它对使用它的公司最友好，还包含专利授权） | 还要检查底层用到的第三方代码（压缩库、加密库）的许可是否兼容 |
| 说话的法律风险 | 声称"符合某某法规"会给自己惹麻烦 | 严格用词：说"提供打码能力"，不说"保证合规" |

## 第六章 别人是怎么做的，学什么、躲什么

### 6.1 腾讯 XLog

**要学的：**

1. **文件开头写清楚"这是什么文件、第几版、怎么压缩加密的"**——这是"不上锁"最起码的要求。
2. **按天/按大小切文件**，再加"总大小上限 + 最多留几天"两道保险。
3. **配了一个独立的 Python 解码脚本**——这是整个行业里最值得抄的一招。它等于在说"我的格式写得足够清楚，清楚到能用另一种语言重新写一遍"。
4. **随包附带代码混淆配置**，用户不用额外折腾。

**要躲的：**

1. **弃坑了**（2018 年之后基本没动）。弃坑的原因不是技术，是**没有维护预算、没有公开的支持承诺**。我们必须在文档里公开"支持哪些版本、多久发一次版"，做不到就主动说。
2. **没发到公共软件仓库**（我查过，确实没有）。用户只能靠拷源码用，这本身就是"没人用"的主要原因。
3. **只支持两种手机芯片**，模拟器之类的地方不方便。
4. **加密跟固定密钥绑在一起**：既不安全，也不算可选。

### 6.2 美团 Logan

**要学的：**

1. **整套"回捞"思路**：采集 → 切片 → 上传 → 服务端解析 → 定位问题，串成一个闭环。我们不做平台，但要**给这套流程留出口**（导出格式、批量导出工具、能接到任意后端的接口）。
2. **有人长期维护**，这是它相对 XLog 最大的优势，也是我们最缺的。
3. 端上处理大日志的工程经验（怎么切片、怎么压缩）。

**要躲的：**

1. **必须搭他家服务器才能解密**——这就是"上锁"的教科书案例。我们的解码工具必须**在完全没有我们服务的情况下也能用**。
2. **强制加密、不能关**。默认安全没问题，但不该不让人选。
3. 跟自家平台绑太紧，外人自然不想用。

### 6.3 MXLogger（个人开发者做的）

**要学的：**

1. **一套底层代码，多个平台共用**——这跟我们想做的事情结构一样。它证明了**这种路子在个人开发者手里也是能跑通的**，这对我们是个正面的证据。
2. 存储和序列化分得比较清楚。
3. 文档里说它速度很好。

**要躲的/要重新想的：**

1. **社区小、文档少**。这提醒我们：文档和格式说明是一等交付物，不是附赠品。
2. **它用的那种表格格式（FlatBuffers）在我们场景里是浪费**（前面 3.5 解释过）。
3. **它选的加密方式不检查内容有没有被改过**。以后我们真要做加密，得重新选。

### 6.4 货拉拉 Glog

**要学的：**

1. **同步和异步两种模式都给**。这个建议采纳，但语义要写清楚：异步模式的好处是快、不拖累主程序，代价是"断电时最后几条可能还没落到硬盘上"——**这个代价必须写进文档，并且给出具体数字**（比如"最多丢 N 毫秒内的日志"）。
2. 跨平台的抽象方式、按天切文件的策略。

**要躲的**：文档太少（这是小型库最常见的死因，而且补救成本极低）。另外注意它跟**谷歌的 glog 同名**，以后写选型文档时要区分开，我们自己起名也要躲开。

### 6.5 调研里漏掉、但值得我们看的

| 是什么 | 为什么值得看 | 对我们的启发 |
|---|---|---|
| **NanoLog**（大学做的低延迟日志系统） | 它的思路是：**写日志的时候不要拼字符串**，只在纸上记一个编号和几个数字，等真的要看日志的时候再去查编号对应的原文 | 这才是"写得快"的真正诀窍，比"用 mmap + 压缩"更本质。可以作为第二版的进阶目标（但代价是要做编译器插件，很难） |
| **Perfetto**（谷歌的系统追踪工具） | 它把"数据格式"和"查看工具"彻底分开，谁都能量产自己的查看器 | 这正是我们想做的"不上锁"的工业级样板 |
| **安卓自带的日志系统** | 它每写一条日志都要跨进程送给系统，有固定开销，还有限流 | 说明"自己写文件"仍有价值。同时要决定：默认是"既写到系统日志也写文件"，还是"只写文件"（建议：开发版两个都写，正式版只写文件） |
| **iPhone 自带的日志系统** | 苹果自己有一套，甚至能读历史日志 | 说明我们在苹果上不是唯一解。文档里必须讲清楚"比它多什么"：格式统一、能自动打码、能导出、能独立解码 |
| **swift-log**（苹果生态的日志标准接口） | 苹果开发者习惯用它 | **这是最好的接入点**：给它做个对接件，苹果开发者一行代码就能把日志接到我们这边 |
| **SLF4J / Kermit / Napier** | 都是现成的日志门面 | 同上：**给它们做对接件，而不是跟它们抢位置** |

### 6.6 最关键的一招：别抢位置，去当别人背后的"仓库"

前面说了，一百个 App 只有 3.4 个用第三方日志工具。想让这个数字变好，唯一的办法是：

**不要要求用户换工具，要寄生在他们已经在用的工具上。**

| 用户现在用什么 | 我们怎么接进去 | 用户要改多少代码 |
|---|---|---|
| Timber | 写一个插件挂上去 | 一行 |
| SLF4J / kotlin-logging | 写一个后端 | 加一行依赖 |
| swift-log（苹果） | 写一个处理器 | 一行 |
| Kermit（跨平台） | 写一个输出端 | 一行 |
| 安卓自带的日志 | **不要求换接口**，用写代码时的检查 + 运行时打码 | 零（改构建配置） |

## 第七章 需要你拍板的几件事

每件事我都给了建议，但决定得你来做。

**第 1 件：底层用哪门语言？**

选项：C++ / Rust / 纯 Kotlin。
C++ 好找人，但容易出内存问题、而且容易被那个"测试期功能"诱惑；Rust 更安全、还会逼你走稳的路，但要学；纯 Kotlin 最省事但速度上不去。

**我的建议**：团队没有现成的 C++ 积累就选 Rust。但更要紧的是——**先花两周做实验，用实测数据决定，别凭感觉。** 而且先把"接口标准"和"格式说明"定死，这样这个决定随时可以改。

**第 2 件：跨平台做到什么程度？**

**我的建议**：做成"手机用底层加速版 + 电脑用纯 Kotlin 版"这种分工。理由是能省掉六份包的维护工作。

**第 3 件：加密怎么办？**

**我的建议**：第一版不做，只留位置，并且写清楚"我们能防什么、防不了什么"。这是我最坚持的一条建议。

**第 4 件：日志内容用什么格式装？**

**我的建议**：自己定外层规矩 + 里面用 Protobuf + 能导出成人能读的版本。不用 FlatBuffers。

**第 5 件：查看工具做成什么样？**

**我的建议**：第一版只做"格式说明 + 命令行工具 + Python 独立解码器"，图形界面放到第二版。

**第 6 件：跟监控平台对接做到什么程度？**

**我的建议**：第一版只做"翻译"和几个接口，现成的对接插件放第二版，而且必须单独发一个包。

**第 7 件：打码默认开还是默认关？**

**我的建议**：给字段打标记的（最准）默认开；扫自由文字的默认也开，但只用一小套规则并先做便宜筛选；"全都扫一遍"这种严格模式让人自己选。另外补上"写代码时检查"这一手。

**第 8 件：支持哪些平台？**

**我的建议**：第一版**安卓先行、苹果跟上**；**电脑/服务端放到第二版**（第一版没有落盘引擎，用不到它）。砍掉 Flutter、网页版、Windows 的底层加速版。

**第 9 件：最低支持哪个安卓版本？**

文档里写的是 21，但项目壳子里其实是 24。**建议直接按 24 来**（除非你确实有 21 到 23 的用户），不然承诺了就得测。

**第 10 件：什么叫成功？**

**我的建议**：自己项目生产环境用起来了就算成功，别人来用算加分。这两个目标的做事方式完全不同，混着来一定会失控。

**第 11 件：要不要拿 XLog 的代码改？**

**我的建议**：不要。它的格式旧、密钥写死、不支持跨平台、没有打码，而且你还得背上"跟着一个停更项目走"的包袱。**但它的设计经验可以拿来参考。**

**第 12 件：开源许可和协作规则？**

**我的建议**：Apache-2.0。仓库地址用简单的那种（不用验证域名）。把支持哪些版本、多久发一次版公开出去，并且提前想清楚"什么时候该宣布进入维护模式"。

**第 13 件：苹果那边要服务到哪一步？**（新增，来自源码体检的发现）

两种做法，工作量差很多：

- **只服务 Kotlin 跨平台项目**：库通过公共仓库发一个 Kotlin 编译产物就够了，用户在自己项目里打包时自动生成苹果用的包。**我们几乎不用额外做什么。**
- **还要服务纯 Swift 项目**（完全不用 Kotlin 的项目）：必须额外做 XCFramework 打包，还要配 SPM 和 CocoaPods 两种接入方式。这是一大块工作（大约占整个第三阶段的一成半）。

**我的建议**：第一版只服务 Kotlin 跨平台项目。理由很直接——纯 Swift 项目本来就不会选一个 Kotlin 写的日志库，为它们做打包，等于花一成半的工作量去服务一小撮不会来的人。等真有纯 Swift 用户找上门再加，而且那时我们已经知道该怎么加。

## 已经定下来的四件事（你已确认）

### 定案一：第一使用者是**外部用户**（陌生人）

**你说选外部用户。这一条最重，它带来三条硬要求，同时也带来一个必须直面的矛盾。**

**三条硬要求：**

| 要求 | 具体含义 |
|---|---|
| **接口一旦发出去就基本改不动** | 陌生人不会给你"改一下我这边适配"的机会。第一版之前必须把接口形状想清楚，之后靠约束 17（对外接口快照）守住 |
| **不能假设别人的架构跟你一样** | 别人家可能只有一个模块，也可能有二十个。所以"来源维度"必须**由用户自己定义名字**，不能写死成我们的"组件/路由"概念 |
| **默认值必须保守、错误必须可感知** | 陌生人的项目里什么情况都有。没初始化不许崩、写失败不许静默吞、版本不兼容要明确报错 |

**必须直面的一个矛盾（重要）：**

我们最有价值的差异化是"**按模块看日志、按链路串日志**"。但这两条预设了使用者**有一套组件化架构**——

> **而大多数外部用户没有。他们只有一个 app 模块，一条链路就是"用户点了一下"。**

所以对外不能把"模块化"当主打招牌，必须这样设计：

- **来源维度做成"用户自定义"**：有架构的人可以定义成"网络/支付/路由"，没架构的人可以只定义一个默认的，甚至不用。**我们不预设，只提供能力。**
- **对外主打的排序应该是**：① 打码（合规刚需，零迁移）② 链路串联（每天找日志的痛点，对任何规模的 App 都成立）③ 零迁移对接件 ④ 来源维度（加分项，给有架构的团队）

**这条如果你认可，我会按这个排序去改所有对外文案。**

### 定案二：链路号的自动传递——**做**

这是输出端最大的价值点，也是现有工具**全部没做**的那一件事。做法是挂在协程自带的"随身便签"机制上，跨协程自动带着走；跨线程的边界需要额外处理一次。开发者只在业务入口标记一次，中间的代码一行都不用改。

### 定案三：桥接——**做，而且支持多种模式**

不跟 Timber / Kermit / SLF4J / swift-log 抢位置，给它们都写对接件。

"支持多种模式"我的理解是这两种都要（如果不对请纠正）：

1. **别人打进我们**：用户继续用 Timber，但日志最终进我们的体系——**这是零迁移采用的通道**
2. **我们转发出去**：用户想让我们体系里的日志也走他原有的通道——**这是"不绑架用户"的保证**

而且**用户应该能只用其中一块**：只用打码、只用检查、只用输出端，都行（对应约束 14）。

### 定案四：最近 N 条的环形缓冲——**要**

成本低（就是内存里存最近几千条），收益大：它回答"刚才发生了什么"，而且是**通往第二版落盘的天然接缝**——环形缓冲的内容写进文件，就是落盘。

顺带说一个它撑不住的场景，避免误解：**进程被系统杀掉时，内存里的环形缓冲一样会丢。** 只有第二版的内存映射才能撑过被杀。所以第一版对它的定位是"调试用"和"过渡用"，不是"线上排障的最终方案"。

## 附录 A：开工前要定死的规矩

这些是"不管后面怎么改，都不许破的规矩"。之所以要提前定，是因为它们决定了以后能不能换语言、能不能换格式、会不会上线崩。

1. 上层和底层之间，只用最基础的接口，不用花哨的、还在测试期的那些
2. 写日志要分层：先攒着 → 再拼格式 → 再压缩 → 最后落盘
3. 文件开头必须写清楚：这是什么文件、第几版、怎么压缩的、时间基准是什么
4. 每条记录都要带长度和校验，读到坏的地方能往后跳，烂掉的尾巴能安全丢掉，**而且丢掉多少必须报数**
5. 写之前先占好位置，不许出现"硬盘满了程序崩掉"
6. 一个进程一个文件，不做多进程共用
7. 时间要记两套：精确流逝时间 + 墙上时钟，时钟被改动也要记
8. 打码要在最早的位置做：能标记的字段，在内容变成日志之前就处理掉
9. **不做全局配置**（别人的日志库就有这个问题：两个库抢一个全局设置，互相覆盖）
10. 默认就是安全的：默认不采集、默认打码开启、默认不加密但留好位置
11. 不依赖任何界面框架和生命周期框架
12. 大版本不兼容就直接拒绝读；小版本加的新内容，老版本要能跳过

## 附录 B：测速怎么测才算数

防止"自己给自己打分"：

1. **分开报**：上报"业务线程感知到的耗时"和"落盘速度"两个数，不许混成一个漂亮数字
2. **报分布，不报平均**：至少给"一半的情况""最慢的 1%""最慢的千分之一"三个数
3. **条件固定**：同一款手机、同一个包、正式版、关掉调试器、飞行模式、清空后台，并且说明温度和电量
4. **对比对象写清楚**：至少包括安卓自带日志、一个纯 Kotlin 版本，最好把 XLog 这些也编出来比
5. **公开脚本和原始数据**，给出机型清单
6. **主动说明什么情况下会变慢**（低端机、硬盘快满、压缩级别调高）——这才叫可信
7. 每次发大版本都重新测一遍，跟上次对比（速度退步和功能出错一样严重）
