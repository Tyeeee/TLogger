# TLogger 技术可行性分析与架构方案设计报告

> 状态：决策稿 v1.0（待发起人拍板）
> 阶段：可行性分析 / 方案设计（未动工）
> 分析基线：当前工作区 `TLoggerDemo` 脚手架实测状态 —— Gradle 9.5.0、AGP 9.3.0、Kotlin 2.2.10、compileSdk/targetSdk 37、minSdk 24、JVM target 11、Compose BOM 2026.02.01；工作区尚未初始化 Git 仓库
> 本报告不含任何代码，仅作技术判断与决策依据

---

## 0. 结论摘要（先看这一页）

**判定一：四个差异化点可以在同一个代码库里共存，不存在根本性的技术冲突。**
两两交互逐对分析后，只有一处是"不能用工程手段消解、必须做产品级取舍"的真冲突：**加密 × 无供应商锁定**。其余都是"有工程张力但可解"。

**判定二：四个差异化点全部在 V1.0 交付不现实。**
不是技术不可能，而是**验证与维护矩阵**超过单人承载能力（约 15–20 个二进制产物变体 × 每年多轮上游破坏性变更）。V1.0 现实的交付量是"2.5 个"：持久化内核 + 无锁定格式 + 脱敏；加密与 OpenTelemetry 后置到 V2。

**判定三：如果只能先做一个差异化点，选"隐私合规（声明式脱敏 + 编译期泄漏检测）"。**
它是唯一一个**不需要用户迁移任何 API 就能被采用**的能力（可作为 Android Lint 规则、脱敏运行时、Timber Tree/SLF4J Provider 桥接独立分发），实现成本最低、不依赖 Native 核心、且直接对应市场调研中被实证量化过的最大空白。

**判定四（反直觉，但必须说）：调研中的"空白五（ZSTD）"不是差异化点。**
ZSTD 换掉 zlib 是一次一小时的工程选择，任何人都能在一个周末复制，不能作为定位。同时"空白三（KMP + 高性能持久化）"是**需求最弱**的空白：滑铁卢大学 2025 年的实证研究显示，在 48,702 个 Google Play 应用中，采用第三方日志库的应用仅占 **3.4%**（详见 §2.1）。把路线图与成功标准建立在"KMP 人群会来用"的假设上，是本项目最大的战略风险。

**判定五：真正的护城河不是代码，是"可验证性"。**
建议把定位中的第四点从"无供应商锁定"升级为**"可验证的无锁定"**：格式规范（SSOT）+ 黄金样本 + 一致性测试 + 独立编写的第二实现解码器 + 可复现基准。这是唯一难以被抄袭的资产（抄袭者要抄的是规范与测试，而不是几百行 C++）。

**一句话结论：** 条件可行。技术路线清晰、风险可枚举，但**范围必须由维护预算倒推**，而不是由"尽善尽美"的功能清单正推。若坚持 V1.0 一次交付四点，项目大概率在 P3（Apple 平台 + 发布矩阵）阶段失去动力，代价是全部前期投入。

## 1. 可行性分析

### 1.1 四个差异化点的两两交互矩阵

判定标准：
- **正交**：可以各自独立设计，互不影响；
- **工程张力**：会互相施加约束，但存在明确的工程解法；
- **根本冲突**：约束直接互斥，只能靠产品定义取舍。

| 交互对 | 判定 | 冲突的具体形态 | 解法 |
|---|---|---|---|
| 高性能持久化 × KMP | **工程张力** | 跨 FFI 边界的调用成本会吃掉 mmap 的收益；Kotlin/Native 的 C 库导入目前处于 **Beta**，且与 Kotlin/Xcode 版本强耦合 | 批量跨越边界（1 次调用承载 N 条记录）；只暴露 C ABI；不用实验性 C++ interop |
| 高性能持久化 × 隐私合规 | **工程张力（最强的一处）** | 脱敏 = 必须扫描内容；全量扫描与"零拷贝写"直接对立 | 三级脱敏：声明字段在 API 层就地脱敏（值不进缓冲）/ 自由文本在编码后落盘前扫描 / 快速预筛（长度·字符集·校验位） |
| 高性能持久化 × 无锁定 | 正交 | 仅要求格式自描述、算法字段可预留 | 文件头显式携带算法/编解码/schema/页大小等 id |
| KMP × 隐私合规 | 正交 | 脱敏规则是纯函数，天然适合 KMP 共享代码 | 规则集放 KMP 层，扫描器可下沉 Native |
| KMP × 无锁定 | 正交 | — | — |
| 隐私合规 × 无锁定 | 正交（且互相强化） | 默认"明文 + 脱敏"会同时强化"任何人可解析"与"PII 不落盘" | 这正是 V1 的正确默认组合 |
| 加密 × 无锁定 | **根本冲突（唯一）** | "无锁定"= 任何人无需本项目的服务与密钥即可读取；"加密"= 只有持密钥者可读 | 见下方专述 |

**关于"加密 × 无锁定"的专述（本报告最重要的判断之一）：**

这一对不是技术问题，是**密钥托管悖论**：

1. 若密钥硬编码在 SDK 内或从应用常量派生 → 攻击者可从 APK 提取，加密**退化为混淆**，但它同时消耗了"独立解密工具"的可行性（工具仍需密钥，而密钥既然公开，加密就没有意义）；
2. 若密钥由服务端下发或托管 → 立刻变成 Logan 模式（必须自建服务端、供应商锁定），与差异化点四直接背叛；
3. 两者之间只剩一种自洽形态：**本地密钥 / 用户口令加密**，其安全上限是"设备被物理取得但应用沙箱未被攻破"级别。

因此结论是：**加密可以作为能力存在，但不能作为卖点，且必须公开威胁模型**。把它宣传成"安全"就是安全剧场（security theater），这在开源领域尤其容易招致声誉损失。V1 的处置：格式预留算法与密钥槽字段、交付威胁模型文档、**不实现加密算法本身**。

### 1.2 复杂度是否超出个人/小团队承载

需要长期维护的矩阵（按 V1 若全量交付估算）：

| 维度 | 变体数 | 说明 |
|---|---|---|
| Android AAR（含 Native） | 3–4 | arm64-v8a、armeabi-v7a、（可选 x86_64 供模拟器/Chromebook） |
| Apple XCFramework | 3 平台 × 2 架构 | iOS device / iOS simulator / macOS，各含 arm64 与 x86_64（或 universal） |
| JVM 桌面（若带 Native） | 3 OS × 2 架构 = 6 | Linux/macOS/Windows × x64/arm64；**这是压垮矩阵的一项** |
| KMP 元数据与 Gradle 变体 | 1 套（对应上列全部） | 变体匹配、属性消歧、缺失变体报错 |
| 构建工具链 | Gradle 9.x + AGP 9.x + Kotlin 2.x + NDK + Xcode | 任一大版本升级都是一次完整回归 |
| **合计** | **约 15–20 个二进制产物变体** | 每个都要签名、发布、验证可消费 |

真实维护成本估算（单人）：
- **仅"跟进上游破坏性变更"**（Kotlin/AGP/Xcode/NDK 每年合计 4–8 次有效破坏点）：约 8–16 小时/月；
- Issue 与 PR 响应、版本发布、文档同步：约 8–12 小时/月；
- 结果：一个月不发版，社区信任就开始衰减；三个月不发版，项目在事实上被判定为"弃养"——而这正是调研中 XLog 被淘汰的原因（**我们必须避免让自己成为新的 XLog**）。

**结论：不超出技术能力，但超出 V1.0 时间窗内的交付能力。** 必须分阶段，并且第一阶段就要砍掉最贵的矩阵项（JVM 桌面 Native 分发）。

### 1.3 构建/调试/发布中"未预见"的障碍清单

这一节是调研阶段最容易漏、开工后最伤人的部分。以下每一条都应在 P0 阶段验证或排除。

**A. Kotlin/Native 互操作的成熟度，比预期低**
- 官方文档明确：C 与 Objective-C 库的导入**当前处于 Beta**，理由是"使用 C/ObjC 库可能影响代码与不同 Kotlin 版本、依赖、Xcode 版本的兼容性"（[C, Objective-C, and Swift library import](https://kotlinlang.org/docs/native-lib-import-stability.html)、[Interoperability with C](https://kotlinlang.org/docs/native-c-interop.html)）。cinterop 生成的声明需要 `@ExperimentalForeignApi` opt-in。
- 由此派生的具体坑：**每个 Kotlin 版本只与一个 Xcode 版本最匹配**；Xcode 比推荐版本新时，"导入第三方 native 库"经常直接不可用；Kotlin/Native **不区分 api/implementation**，native 依赖一定是 api 依赖，会传递到用户项目并可能符号冲突；**禁止内嵌静态库**（一旦内嵌，用户无法排除或替换）；库的公开 API 中不应出现 native 类型（官方明示"未来会破坏这类用法"）。
- 这些不是"可以注意一下"的细节，而是**强制的架构约束**：库的对外 API 不得出现任何 native 类型；native 依赖不得传递；包名必须自定义隔离。

**B. Android 16 KB 页大小（2026 年的硬性项）**
Google Play 已要求面向 Android 15+ 的应用支持 16 KB 页大小，native 库需按 16 KB 对齐（参见 [16KB Page Size 升级指南](https://bugly.tds.qq.com/docs/tutorial/Android/16kb_version/)）。对我们的直接影响：
- 核心层**不得硬编码 4 KB 页大小**做映射对齐或偏移计算，必须运行时读取实际页大小；
- NDK 需使用 28+（默认 16 KB 对齐），CI 需增加对齐校验（zipalign/elf 段对齐检查）；
- 这一项如果做错，故障形态是"在老设备上正常、在新设备上启动崩溃"，极难归因。

**C. mmap 的代价：SIGBUS**
mmap 写文件的经典故障是"文件空间不足时写入映射页触发 SIGBUS 直接杀进程"，LevelDB 就曾记录过 `ftruncate` + mmap 在磁盘空间不足时 `Append()` 崩溃的问题（[google/leveldb#150](https://github.com/google/leveldb/issues/150)）。定位上必须接受：**mmap 的性能收益，是用"必须自行处理空间不足"换来的**。处置策略见 §1.4 与 §6。
反之，mmap 也有别处买不到的好处：写入映射页后数据进入页缓存，**进程崩溃（非掉电）不丢数据**，这是"崩溃前后现场"能力的物理基础。

**D. iOS 的生命周期与文件保护**
- 文件保护级别：默认的 `NSFileProtectionComplete` 会让**设备锁屏后文件不可读，写入直接失败**——日志库必须显式选择 `CompleteUntilFirstUserAuthentication` 或更低级别，这是一个必须写进文档的安全权衡；
- 后台挂起、jetsam 内存回收、被系统杀进程前的 flush 窗口；
- 日志文件应排除 iCloud 备份（否则用户备份体积异常，且把可能含 PII 的日志同步上云）；
- iOS 上存在系统级替代品：`OSLog` 与 `OSLogStore`（可读本进程历史日志），需在方案中明确"我们比它多什么"（跨平台一致格式、独立解码、可自定义脱敏、可导出）。

**E. JVM 桌面的分发负担**
如果 JVM 目标也引入 Native 核心，就要为 Linux/macOS/Windows × x64/arm64 打包并加载 native 库，还要面对 Windows 上"映射文件无法删除/无法截断"、以及 JVM 没有显式 unmap 的 API（映射区释放依赖 GC 与 `Cleaner`）等平台差异。**处置建议：JVM 目标使用纯 Kotlin 引擎（`FileChannel.map` + 预分配），与 Native 核心共享同一格式规范。** 这一条把矩阵从 ~20 个变体压回 ~8 个。

**F. Maven Central 发布**
- OSSRH 已终止服务，新项目必须走 **Central Portal**（[OSSRH Sunset](https://central.sonatype.org/pages/ossrh-eol/)）；
- KMP 库的发布要处理多平台变体元数据、`-sources`/`-javadoc` 产物、GPG 签名、模块元数据完整性，发布失败点比单平台库多得多；
- Android 变体需发布 AAR 且保证 consumer ProGuard 规则随包提供；
- **本报告已复核：腾讯 XLog（`com.tencent.mars:mars-xlog`）与美团 Logan 均未出现在 Maven Central 索引中**（`repo1.maven.org` 对应路径 404；`search.maven.org` 查询 `mars-xlog` 命中 0 条）。调研中"未发布 Maven Central"的判断成立——这既是机会，也提醒我们发布环节是这类库的常见死穴。

**G. 调试与符号化**
Native 崩溃栈的符号化、Android tombstone 与符号表、iOS dSYM、R8 混淆后的类名与日志中的调用位置采集（自动 TAG 与调用栈采集在 R8 下容易失真）——这些都要在 P1 就形成固定流程，否则第一次线上 native 崩溃就会消耗数天。

**H. 版本基线的现实偏差**
约束文档写的是"AGP 8.0+ / Gradle 8.0+"，但当前脚手架已经是 **AGP 9.3.0 / Gradle 9.5.0**（AGP 9 引入了新 DSL，如 `compileSdk { version = release(37) }`、`optimization {}`），而 Kotlin 在脚手架里是 2.2.10，官方文档站当前版本是 2.4.20。**版本策略必须在 P0 明确**：以哪个 Kotlin 为最低支持基线、以哪个 Xcode 为推荐版本，并写进支持矩阵文档。否则"用户用 AGP 9 + Kotlin 2.4 时变体匹配失败"会成为最高频的 issue。

### 1.4 可行性结论

| 维度 | 结论 |
|---|---|
| 四点整合 | **可行**，但唯一真冲突（加密 × 无锁定）必须靠产品定义取舍，不能靠工程消解 |
| 技术风险 | 中：主要来自 Kotlin/Native 互操作的 Beta 状态与 native 崩溃面，均可通过"只走 C ABI + 严格边界纪律 + fuzz/sanitizer CI"约束到可接受 |
| 工程风险 | **高**：范围 × 矩阵 × 单人维护，是本项目第一位的风险（高于任何纯技术风险） |
| 何时应放弃自研 | 若目标只是"自己 App 里日志更好用"，fork/集成 XLog 或直接用 Glog/MXLogger 的成本收益比更优；自研的正当性来自"格式自有 + 脱敏内置 + KMP 统一"三者的组合，缺一即不成立 |
| 建议 | **分阶段交付**：V1.0 交付"持久化内核 + 无锁定格式 + 脱敏"（2.5 点），V2 补齐加密与 OTel |

## 2. 进入架构前的市场前提校准

调研结论大方向成立，但有三处偏差会直接影响优先级判断，必须先修正。

### 2.1 数据校准

滑铁卢大学 2025 年的实证研究（[UWSpace 条目](https://uwspace.uwaterloo.ca/items/b2b89af2-ce8b-42c6-9dae-7c771200e59c)、[全文 PDF](https://dspacemainprd01.lib.uwaterloo.ca/server/api/core/bitstreams/dd05e5b3-d299-4e95-973f-0ba688661e50/content)）摘要原文要点：

- 样本：Google Play **48,702** 个应用；**采用第三方日志库的应用仅占 3.4%**；
- 在启用了日志库的应用中，**49.3% 存在隐私泄漏**（注意：49.3% 是"有泄漏的应用比例"，不是"泄漏涉及用户信息的比例"）；
- Timber 35.2% / SLF4J 35.1% / Firebase 29.4%，三者合计 **99.7%** 的已验证泄漏实例；
- 泄漏主要来自**间接数据流（62.5%）**，路径复杂度多为 2–4 条语句；
- 来源上 **用户信息（user-info）占 69.7%**，**用户输入（user-input）占 30.3%**。

修正与推论：
1. 调研表中的"近半（49.3%）涉及用户信息"应修正为"49.3% 的启用日志库应用存在泄漏"；用户信息源占比是 69.7%。这个修正不削弱结论，反而**强化**：69.7% 的泄漏源头是用户信息字段，声明式字段级脱敏的收益比想象中更大。
2. **3.4% 的采用率是本项目最重要的战略数字**。它意味着"做一个更好的日志库"这件事的天花板极低；而"**让不使用日志库的 96.6% 也能降低日志泄漏**"才是真正的增量空间。
3. **62.5% 的泄漏是间接数据流、2–4 条语句路径** —— 这恰恰是**静态分析**（Android Lint / 编译器插件）最擅长、运行时脱敏最难覆盖的形态（运行时只能看到已经拼好的字符串）。因此第一优先级能力应当是"编译期检测 + 运行期兜底"的组合，而不是单纯的运行期正则脱敏。这是本报告对调研结论的第一个实质性推进。

### 2.2 空白点的价值重排

| 调研空白 | 痛点是真实的吗 | 是差异化点吗 | 建议定位 |
|---|---|---|---|
| 空白一 隐私合规与自动脱敏 | **是**，且已被实证量化 | **是**，且可实现"零迁移采用" | **第一优先级（V1）** |
| 空白二 无锁定的高性能持久化 | 是（开发者选型时的真实顾虑） | 是，但护城河在"规范+测试"而非代码 | **V1（与内核同期）** |
| 空白三 KMP + 高性能持久化 | 弱（KMP 生产规模小，且多已用 Sentry/Crashlytics） | 是交付形态，不是购买理由 | V1 保证三端可用，不做营销主轴 |
| 空白四 结构化日志与可观测性集成 | 中（趋势真实，但 OTel 自身仍在演进） | 半差异化（SLF4J 2.x 已有 Key-Value API、KMP-Logger 已有结构化） | V2 交付导出适配器 |
| 空白五 ZSTD 替代传统方案 | 低 | **否**，一小时可复制的工程选择 | 实现选择，不作卖点 |

### 2.3 命名风险（易被忽视，但代价高）

- "Glog"已被两个不相关的项目占据（Google glog 与货拉拉 Glog），说明该命名空间拥挤；
- "Logger"、"Kermit"、"Napier" 等已占用常见词；
- "TLogger" 需要在 Maven Central、GitHub、npm（若未来有 JS 端）、以及商标库中做检索；groupId 建议使用 `io.github.<user>`（无需域名验证，且迁移成本低）。

## 3. 架构方案对比

### 3.1 共同骨架：先冻结不变量，再选实现语言

无论选 C++、Rust 还是纯 Kotlin，**架构骨架必须相同**。先把下列不变量冻结（这也是把语言决策"降级为可替换实现细节"的关键手法）：

| 编号 | 不变量 | 理由 |
|---|---|---|
| I1 | 唯一 FFI 边界为 C ABI；STL/异常/RTTI/panic 不得穿越边界 | 规避 Kotlin/Native Beta 与 Xcode 耦合风险；panic 跨 FFI 是未定义行为 |
| I2 | 写路径分层：API → 无锁环形缓冲 → 编码 → 压缩 →（预留加密）→ mmap | 让 JNI 穿越成本被批量摊薄；让压缩/加密可关闭 |
| I3 | 格式自描述：魔数、版本、字节序、页大小、编解码 id、算法 id、密钥 id、schema id、时钟基准 | "无锁定"的物理实现 |
| I4 | 每条记录自带长度与校验；读取端前向扫描恢复；尾部截断可安全丢弃且**必须计数上报** | 崩溃/掉电安全；"永不静默丢数据" |
| I5 | 所有映射写前预分配与预留空间，写前检查剩余配额 | 规避 SIGBUS |
| I6 | 单进程单文件分片 + 清单文件；不做跨进程共享映射 | 规避多进程锁与竞态 |
| I7 | 单调时钟定序 + 墙钟定显示 + 记录两者偏移与时钟跳变事件 | 日志时序正确性（跨文件归并的前提） |
| I8 | 脱敏尽早就位：声明字段在 API 层就地脱敏（值不进缓冲），自由文本在落盘前扫描 | 让"脱敏"真的减少暴露面，而不是把裸值在内存里搬来搬去 |
| I9 | 无全局可变单例；配置随实例 | 规避 Timber 式全局配置冲突 |
| I10 | 未配置即安全：默认不采集、默认脱敏开启、默认不加密但格式预留 | 合规默认值应偏保守 |
| I11 | 核心不依赖任何 UI/生命周期框架（androidx.lifecycle 等） | 约束已明确；也让库可用于任意宿主 |
| I12 | 主版本不兼容即拒读；次版本新增字段必须可跳过 | 长期可演进 |

### 3.2 方案 A：KMP API 层 + C++ 核心（JNI/cinterop）

| 项 | 评价 |
|---|---|
| 优势 | 团队既有认知（Android/NDK 出身常见）；zstd / mbedTLS / BoringSSL / fmt 等生态直接可用；iOS 侧"头文件即契约"；构建可由 CMake + `externalNativeBuild` 统一，Apple 侧由 Kotlin 的 `embedAndSignAppleFrameworkForXcode` 串联 |
| 劣势 | 内存安全完全依赖纪律（本项目要写的是长生命周期、跨线程、直接操作映射内存的代码，正是 C++ 最危险的场景）；异常与 RTTI 必须严格关闭或限制在边界内；**最大的陷阱是"诱惑你使用实验性 C++ interop"**——一旦使用，就把库绑在 Kotlin 最不稳定的特性上 |
| 适用 | 团队已有 C++ 资产（如现成的加解密/压缩模块），或有明确 C++ 维护人力 |
| 交付风险 | 中高 |

### 3.3 方案 B：KMP API 层 + Rust 核心

| 项 | 评价 |
|---|---|
| 优势 | `extern "C"` 边界天然干净稳定，**从机制上避免你误用 C++ interop**；除了 `unsafe` 块外不存在未定义行为类别（而我们的 unsafe 面积可以控制在"映射内存读写"这一小块）；cargo 交叉编译与静态链接（zstd、AES 实现）成熟；`cargo-fuzz` / sanitizer 体验好；可用 UniFFI 生成 Kotlin/Swift 绑定以减少样板（社区已有 [uniffi-kotlin-multiplatform-bindings](https://klibs.io/project/UbiqueInnovation/uniffi-kotlin-multiplatform-bindings) 这类 KMP 绑定方案） |
| 劣势 | 团队学习成本；Kotlin 侧仍然要面对 cinterop 的 Beta 属性（这一点 C++ 方案也逃不掉）；二进制体积需要显式优化（`opt-level="z"` / LTO / strip / `panic=abort`）；与既有 C++ 资产不互通 |
| 适用 | 无既有 C++ 资产、接受前期学习投入、把长期可维护性放在第一位 |
| 交付风险 | 中 |

**关键判断：在"iOS 侧边界"这一点上，Rust 实际上比 C++ 风险更低。** 原因是 Kotlin/Native 的 C++ 互操作是实验性特性，而 C 头文件互操作虽然也是 Beta，但它是**唯一被官方文档完整支持、且被大量库依赖**的路径。Rust 强制你走 C ABI，等于把架构钉在最稳的那条路上；C++ 则时刻存在"顺手用了实验特性"的滑坡。

### 3.4 方案 C：纯 Kotlin（放弃 Native 核心）

| 项 | 评价 |
|---|---|
| 优势 | 构建矩阵最小（无 NDK、无 Xcode 二进制、无 ABI 问题、无符号化）；调试体验最好；KMP 纯度最高；开发速度最快（预估比 A/B 快 40%+）；无 native 崩溃面（这是本项目第一位技术风险的直接消除） |
| 劣势 | Android 侧：Kotlin/JVM 无法直接 mmap（`MappedByteBuffer` 可用，但 unmap 依赖 GC，Windows 上文件句柄释放不确定）；每条日志需格式化字符串 → **真正的性能瓶颈恰恰在 Kotlin 侧的字符串构造，而不是落盘**；iOS 侧：Kotlin/Native 可以用 POSIX `mmap`/`write`，但需要 `@ExperimentalForeignApi` opt-in，且 Kotlin/Native 的 GC 与内存分配对高频小对象不友好 |
| 性能上限 | 落盘吞吐可以做到"够用"（预分配文件 + 批量序列化 + 无分配编码，理论上可达数万条/秒级），但**"对标 XLog/Logan"的宣称站不住**，尤其在高频短日志场景 |
| 适用 | 若把"合规与可验证"而非"极致性能"当作第一卖点，方案 C 是**投入产出比最高**的路线 |
| 交付风险 | 低 |

### 3.5 方案 D（本报告推荐）：分层内核 + 按平台选择实现

不把 A/B/C 当作互斥选项，而是把它们放进同一个架构：**引擎层是可替换实现（SPI）**。

| 目标平台 | V1 引擎实现 | 理由 |
|---|---|---|
| Android | Native（Rust 或 C++，见 §7 D1） | 性能主战场；ABI 可控（3–4 个） |
| iOS / macOS | 同一 Native 核心 | 与 Android 共享引擎，收益最大化 |
| JVM 桌面/服务端 | **纯 Kotlin 引擎**（`FileChannel.map` + 预分配 + zstd-jni） | 直接砍掉 6 个 native 产物变体，收益远大于性能损失 |
| 测试与降级 | 内存引擎（可注入故障） | 支撑混沌测试与"磁盘不可用时降级"策略 |

方案 D 的实质：**把 §3.1 的不变量与 §3.6 的格式规范做成真正的架构边界，让"引擎实现"成为一个可以在 2 周内替换的细节**。这样做的额外收益是：如果 P0 验证发现 Native 路线不达标，可以退到方案 C 而不推翻架构——**这是本项目最重要的风险对冲手段**。

### 3.6 方案对比总表

| 维度 | A：C++ 核心 | B：Rust 核心 | C：纯 Kotlin | **D：分层内核（推荐）** |
|---|---|---|---|---|
| 交付风险 | 中高 | 中 | 低 | 中（可回退到 C） |
| 性能上限 | 最高 | 最高 | 中 | Android/iOS 最高，桌面中等 |
| 可维护性 | 中（纪律依赖） | 高 | 高 | 高 |
| 构建复杂度 | 高 | 中高 | 低 | 中 |

| 人才可得性 | 高（Android 圈） | 中 | 最高 | 中 |
| 内存安全风险 | 高 | 低 | 低 | 低 |
| 起步到可用 | 中 | 慢 | **快** | 中 |
| 适用场景 | 有 C++ 资产 | 无 C++ 资产、重长期 | 快速验证/合规优先 | **本项目** |

### 3.7 结构化格式选型推演

| 候选 | 优点 | 在本场景下的问题 | 结论 |
|---|---|---|---|
| FlatBuffers | 零拷贝随机访问 | **追加写、顺序读**的场景里，"零拷贝读取"的价值几乎为零；却要付出 schema 工具链、生成代码、可变性受限的代价 | 不采用（MXLogger 用它是因为 Flutter 端 FFI 传结构体方便，与我们目标不同） |
| Protobuf | 演进成熟（字段号 + 可选字段）、紧凑、工具链全、与 OTel 语义天然对齐（OTel 自身即 protobuf） | 需要 schema 管理 | **主编码（V1）** |
| CBOR / MessagePack | 无 schema 自描述、JSON 友好 | 演进纪律弱于 protobuf；类型系统松散 | 备选（自由文本载荷 / 调试导出） |
| 自定义 TLV | 性能最优、完全可控 | 工具链全自建、演进易失控 | **仅用于帧层**，不用于载荷 |
| JSON | 人类可读、工具通用 | 体积与解析成本高 | 作为**导出格式**（CLI 输出），不作为落盘格式 |

**结论：三层设计 = 自定义帧层（自描述、固定语义）+ Protobuf 载荷（可演进）+ JSON 文本导出（人可读）。**
补充一条反直觉判断：**V1 不做索引**。因为按天/按大小分片后单文件可控制在小尺寸，顺序扫描成本可忽略；而"崩溃前后 N 秒回溯"这类能力，V2 只需在文件尾部追加一个轻量索隐块（时间范围 + 级别直方图 + 记录偏移），**不需要引入倒排索引**（那会触碰"不做全文检索"的非目标边界）。

### 3.8 独立分析工具的技术栈

| 形态 | 成本 | 收益 | 建议 |
|---|---|---|---|
| 格式规范文档 + 黄金样本 | 低（1 周） | **最高**；无锁定的真正载体 | **V1 必做** |
| 参考解码器（与核心同语言，随库发布） | 低 | 测试与工具共用；避免两套实现漂移 | **V1 必做** |

## 4. 优先级与路线图

### 4.1 优先级评分（5 分制，分数越高越应优先）

| 高性能持久化内核 | 3 | 4 | 5 | 2 | **5（缺它无库）** | 必做但非卖点 |
| KMP 三端统一 | 2 | 3 | 4 | 2 | 3 | 交付形态 |

### 4.2 如果只能做一个：隐私合规

理由（按重要性排序）：

1. **它是唯一"零迁移采用"的能力。** 其他三点都要求用户更换日志门面/落盘方案（迁移成本极高，3.4% 的采用率已经说明大家对"换日志库"这件事极度保守）；脱敏可以以 Lint 规则、脱敏运行时、Timber Tree、SLF4J Provider 等形式**独立分发**，用户不动现有代码也能用。这直接绕过了"日志库采用率只有 3.4%"这个天花板。
2. **它有实证背书。** 69.7% 的泄漏源是用户信息、62.5% 是间接数据流——这正是声明式字段标注 + 静态检测能覆盖的形态。
3. **它不依赖 Native 核心。** 可以在 6–8 周内独立发货，形成"先有一个能用的东西"的正反馈，避免项目在长达数月的内核开发中失去动力。
4. **它是天然的引流产品。** 先用脱敏模块建立信任与用户，再让用户自然迁移到完整日志库——这是唯一符合本项目资源约束的增长路径。

**注意一个必须诚实面对的现实：** 若第一优先级选合规，那么"高性能持久化"就成了第二阶段的投入，V1.0 的"性能对标 XLog/Logan"宣称应当推迟到 P1 完成、且有可复现基准之后。不要在只有合规模块时就宣称性能优势。

### 4.3 V1.0 边界

**V1.0 必须做：**
1. 格式规范 v1.0 + 黄金样本 + 参考解码器 + CLI + Python 二次实现（可验证的无锁定）
2. mmap + ZSTD 的写入内核（Android + iOS 共享，JVM 桌面用纯 Kotlin 引擎）
3. KMP API 层（Android / iOS / JVM 三端）
4. 隐私合规：声明式脱敏 + 启发式扫描规则集 + 令牌化 + Android Lint 规则 + 可独立分发的脱敏运行时
5. Maven Central 发布 + 支持矩阵 + 桥接（Timber Tree / SLF4J Provider / swift-log LogHandler / Kermit LogWriter）
6. 可复现基准套件 + 威胁模型文档

**架构预留、V1 不实现：**
- AES/SM4 加密（只预留算法 id 与密钥槽字段 + 威胁模型文档）
- OTel 导出适配器（只做语义映射与 TraceContextProvider SPI）
- 压缩字典与分层压缩（热路径 LZ4 / 冷文件 ZSTD 重压缩）
- 文件尾部索引块（"崩溃前 N 秒"视图）
- GUI 查看器

**明确不做（含调研非目标 + 本报告新增）：**
云端上传与分析平台、实时日志流、全文检索、崩溃捕获、Flutter 端（除非出现真实需求）、Windows/macOS/Linux **native** 分发、Web/JS 目标、日志的远程聚合与中心化查询。

### 4.4 分阶段路线图

#### P0 —— 技术验证与技术选型冻结（4–6 周，关键路径起点）

**交付物：**
1. 三组可丢弃的验证原型（Spike）：① 跨边界吞吐与延迟（Kotlin→native 批量 append，测 P50/P99/P999）；② 磁盘满/文件截断/随机字节破坏下的完整性与恢复；③ iOS 端 mmap 在锁屏/后台/杀进程下的行为
2. C ABI 头冻结草案 + 格式规范 v0.1 + 20 个黄金样本
3. 核心语言决策（Rust/C++/纯 Kotlin）—— **基于实测而非偏好**
4. CI 骨架：Android NDK 交叉编译 + Apple 编译 + JVM 测试 + fuzz 冒烟 + 16 KB 对齐校验
5. 版本支持矩阵草案（Kotlin / AGP / Gradle / NDK / Xcode / minSdk）

**验收标准（可量化）：**
- API 侧单条 append P99 ≤ 2 µs（批量跨越 ≥ 64 条/次调用），中端 Android 真机
- 注入 200 次随机 ENOSPC / 截断 / 字节破坏：**进程零崩溃**，可恢复记录 100% 可读，损坏尾部被正确隔离并计数上报
- 800 万条写入后，独立解码器 100% 还原且字段级等价
- iOS 锁屏 30 分钟后台后写入不丢、恢复后可读

**退出条件（重要）：** 任一项不达标 → 调整方案（如放弃 mmap 改用预分配 + 批量 `write`）或缩减范围，**不打折扣地继续推进**。

#### P1 —— 内核与 Android/JVM 打通（8–10 周）

**交付物：** 格式规范 v1.0；写入内核（mmap / 帧层 / 编码 / 轮转 / 配额 / 恢复）；KMP API（Android + JVM）；JVM 纯 Kotlin 引擎；可复现基准套件
**验收标准：**
- 单线程 API 侧吞吐 ≥ 10 万条/秒（不压缩）；压缩后落盘比 ≥ 4:1（典型文本日志）
- 混沌测试 1000 次崩溃注入，零数据静默丢失
- 与 `android.util.Log` 的对比基准公开，且明确标注"在哪些场景不占优"
- AAR 体积增量 ≤ 400 KB（arm64 单 ABI，含 zstd）
- 多进程（2 进程同时写）压力测试无竞态、无数据交错

#### P2 —— 隐私合规模块（5–6 周，可与 P1 并行）

**交付物：** 声明式敏感字段 API；启发式规则集 v1（邮箱 / 手机号 / 身份证 / 银行卡（Luhn 校验）/ IP / URL 凭证 / JWT / 经纬度）；令牌化（HMAC 盐化，可关联不可还原）；Android Lint 规则集（疑似 PII 流入日志）；可独立分发的脱敏运行时 artifact；公开语料库
**验收标准：**
- 公开语料（≥ 2000 条）上：召回 ≥ 99%、精确 ≥ 95%
- 热路径开销 ≤ 5%（P99 增幅）
- 误伤率（正常日志被改写）≤ 2%，且所有改写可在审计报告中回溯
- Lint 在自研项目 + 3 个开源 App 上运行：误报 ≤ 10 条/项目，漏报有明确的能力边界说明
- **脱敏运行时在"不使用本库"的项目中可独立接入**（至少 2 个集成 demo：Timber Tree、`android.util.Log` 包装）

#### P3 —— Apple 平台与 KMP 全量发布（8–10 周）

**交付物：** XCFramework（iOS device/simulator、macOS）；SPM 与 CocoaPods 两种集成；swift-log LogHandler 桥接；iOS 文件保护与后台策略实现；dSYM/符号化流程
**验收标准：**
- iOS 上 API 侧 P99 ≤ 3 µs（A15 级设备）
- 锁屏 / 后台 / 杀进程三种场景各 100 次循环：零丢失
- Swift 侧 30 行内完成接入
- 二进制体积增量 ≤ 1.2 MB（含 zstd）
- Xcode 推荐版本 ±1 的矩阵内编译通过

#### P4 —— 交付与治理（4–6 周，部分与 P1/P2 重叠）

**交付物：** Central Portal 发布流水线；版本与兼容策略；规范文档站点；CLI 工具（解码 / 导出 JSON / 统计 / 校验）；Python 二次实现；公开基准报告；许可与治理文件（Apache-2.0、DCO/CLA、贡献指南、行为准则）
**验收标准：**
- 全新项目在无任何本地依赖的情况下，仅凭 Central 坐标在三端（Android/iOS/JVM 各一个 demo）可用
- Python 解码器与官方解码器在 20 个黄金样本上输出**字节级一致**
- CLI 为单文件二进制，三平台无运行时依赖可执行
- consumer ProGuard 规则随包提供，消费端无额外配置

#### P5 —— V1.0 冻结（2–3 周）

**交付物：** 性能报告（含原始数据与机型清单）、威胁模型文档、三种桥接的接入指南、发布说明、已知限制清单
**验收标准：** 3 名不含作者的开发者，各自在 30 分钟内完成一次接入并成功用 CLI 解码日志

**工作量汇总：**

| 阶段 | 周数 | 关键路径 |
|---|---|---|
| P0 | 4–6 | ★（起点） |
| P1 | 8–10 | ★ |
| P2 | 5–6 | 可并行 |
| P3 | 8–10 | ★ |
| P4 | 4–6 | 可重叠 |
| P5 | 2–3 | ★（终点） |
| **合计** | **约 31–43 周**（单人 60–80% 投入）≈ **7–10 个月** | P0 → P1 → P3 → P5 |

这个时间表与"不追求短期上线、优先长期可维护性"的项目基调一致。**如果期望 3 个月内出 V1.0，则必须砍到只有方案 C + 合规模块——这也是一个合法选择，但要在 P0 就明确，而不是走到一半才发现。**

## 6. 竞品架构深化分析

### 6.1 XLog（腾讯 mars）

**值得借鉴：**
1. **文件自描述与版本化**：魔数、版本、算法标识写在文件头，是"数据不锁死在 SDK 里"的最小充分设计——这是"无锁定"的物理前提；
2. **按天/按大小分文件的滚动策略**，配合"总配额 + 保留天数"的双重上限，避免日志无限增长；
3. **独立 Python 解码脚本**：这一条是整个生态里最值得抄的设计——它证明了"格式规范足够自描述，以至于可以用另一种语言独立实现"；
4. **交付物中包含 ProGuard 规则**，把消费端集成摩擦降到最低。

**必须规避：**
1. **事实弃养**（2018 年后实质停顿）。弃养的根因不是技术，而是"没有维护预算、没有明确的支持矩阵、没有把维护写进计划"。我们必须在文档里公开支持矩阵与发布节奏，并**在无法维持时主动宣布维护模式**；
2. **未发布到 Maven Central**（本报告已复核其 artifact 不在 Central 索引中）。这意味着用户只能源码集成或走第三方镜像——这本身就是采用率的杀手；
3. **ABI 覆盖窄**（仅 armeabi-v7a/arm64-v8a）。在 ARM 设备占绝对多数的今天这不算致命，但对模拟器/CI 与新兴形态（Chromebook、部分平板）不友好；
4. **密钥与加密方式硬编码的倾向**：加密一旦与固定密钥绑定，就既不是安全也不是可选项。

### 6.2 Logan（美团）

**值得借鉴：**
1. **完整的"回捞"流水线思维**：把端上采集、分片、上传、服务端解析、问题定位串成闭环——我们不做平台，但要**为闭环留出接口**（导出格式、批量导出 CLI、可选的"导出到任意后端"钩子）；
2. **活跃维护的组织方式**（明确归属团队、长期投入、多端同步），这是它相对 XLog 最大的优势，也是我们最缺的东西；
3. **端上大日志的分片与压缩策略**，以及[实时日志系统建设实践](https://tech.meituan.com/2022/11/03/logan-real-time-log.html)中关于端上代价的工程经验。

**必须规避：**
1. **强依赖服务端解密**：这是"供应商锁定"的教科书案例。我们的独立解码器必须在**没有我们任何服务**的前提下工作；
2. **强制加密不可关闭**：默认值与可配置性应当分离——"默认安全"不等于"不可选择"；
3. SDK 与自家平台耦合过深导致外部采用意愿低。

### 6.3 MXLogger

**值得借鉴：**
1. **C/C++ 核心 + FFI 多端复用的架构**（[MXLogger](https://github.com/coder-dongjiayi/mxlogger)）——这与我们的方案 A/B 同构，说明该路线在小团队手里确实可以跑通；
2. **序列化与存储分层**的清晰度；
3. 独立维护者在没有大厂资源下的实际交付路径（对我们是正面的可行性证据）。

**必须规避/重新审视：**
1. **社区规模小、文档不足** → 文档与规范必须是一等交付物，不是附属品；
2. **FlatBuffers 的引入**：在本场景（追加写、顺序读）中，零拷贝随机访问的价值被浪费，却增加了 schema 工具链负担（见 §3.7）；
3. **AES-CFB 模式**：CFB 不提供完整性认证。若 V2 做加密，应重新评估模式选择（认证加密优先，或至少明确"无完整性保护"这一事实并写入威胁模型）。

### 6.4 Glog（货拉拉）

**值得借鉴：**
1. **同步/异步双模式**：这是一个应当采纳的设计——但要有明确语义：异步模式提供吞吐与"绝不阻塞业务线程"，同步模式提供"写入即落盘"的可预期性；两模式的**数据丢失窗口必须在 API 文档中量化**（例如异步模式下最多丢失 N ms 或 N KB 的缓冲）；
2. **跨平台抽象层的分层方式**；
3. 按天分文件的策略与生命周期管理。

**必须规避：** 文档不足（这是小型库最常见的死因，且修复成本极低）。另外注意它与 Google glog **同名**，选型文档中必须消歧，我们自己的命名也要避开这个坑。

### 6.5 调研中遗漏、但值得作为架构输入的项目

| 项目/方向 | 为什么值得看 | 对本案的启发 |
|---|---|---|
| **NanoLog** / "编译期日志语句优化"（[Stanford 论文](https://www.web.stanford.edu/~ouster/cgi-bin/papers/YangPhD.pdf)、[NanoLog 镜像](https://github.com/hhy5277/NanoLog)） | 低延迟日志的经典范式：编译期分配日志语句 ID + 静态字符串表，热路径只写入 ID 与参数 | **这是"高性能"真正的技术来源**，比"mmap + ZSTD"更本质。可作为 V2 的性能进阶路线（但需要编译器插件，成本高） |
| **Perfetto / ProtoZero**（[设计文档](https://perfetto.dev/docs/design-docs/protozero)） | 自描述二进制 trace 格式 + 与 SDK 分离的独立查看器 | "格式与工具链分离"的最佳工业范例；直接支撑我们的"可验证的无锁定"定位 |
| **Android logd / liblog** | 日志经 socket 跨进程送到 logd，存在固定成本与限流 | 解释了为什么"自研落盘"仍有价值（logcat 不适合作为唯一归档），也提示了"写入 logcat 与写入文件"两条链路的取舍：**默认双写还是只写文件**需要明确决策（V1 建议：debug 构建双写，release 只写文件 + 可选桥接） |
| **iOS OSLog / OSLogStore** | 系统原生日志存储与历史读取 | iOS 上我们不是唯一解；必须在文档中说明相对 OSLog 的增量价值（跨平台一致格式、可自定义脱敏、可导出、可独立解码） |
| **swift-log**（[文档](https://swiftpackageindex.com/apple/swift-log/1.11.0/documentation/logging#app-main)） | Apple 生态的 facade 标准与 LogHandler SPI | **最佳接入点**：提供 LogHandler 桥接即可被 Swift 生态"零迁移"采用 |
| **SLF4J 2.x fluent API** | 官方结构化 Key-Value 支持 | 结构化日志不是我们的独占空白；与 SLF4J 的关系应是"提供 Provider/后端"，而非竞争 |
| **Kermit / Napier**（[Kermit 讨论](https://github.com/touchlab/Kermit/discussions/217)） | KMP 生态既有的日志门面 | 同上：提供后端桥接，让 Kermit 用户把输出接到我们的引擎 |
| **SQLite 作为日志存储**（[Blacklite 优化实践](https://sqlite.work/optimizing-sqlite-for-high-performance-logging-with-blacklite/)） | "直接用 SQLite"是真实存在的替代路线 | 需要在设计文档中给出**明确的不选理由**：SQLite 的写入路径有 fsync 与锁成本，热路径吞吐与延迟均不如追加式 mmap；但它在"结构化查询"上远胜。结论：V1 可提供一个**调试期 SQLite Sink**（不作为默认），换取开发者体验 |
| Rust 生态（tracing / quill / low-latency-log 等） | 若选 Rust，需评估是否复用其 tracing 生态 | 不建议依赖：我们的语义（脱敏、格式规范、KMP 桥接）与 tracing 的抽象层不同频，强行复用会引入不必要的耦合 |

### 6.6 桥接优先的采用策略（本报告的战术建议）

| 既有门面 | 桥接形态 | 用户迁移成本 |
|---|---|---|
| Timber | 一个 Tree 实现（写入我们的引擎 + 走既有脱敏） | 一行 |
| SLF4J / kotlin-logging | 一个 SLF4J Provider 或 Appender | 加依赖 |
| swift-log | 一个 LogHandler | 一行 |
| Kermit | 一个 LogWriter | 一行 |
| `android.util.Log` | 脱敏运行时 + 编译期 Lint（**不要求换 API**） | 零（构建脚本） |

**这张表是"3.4% 采用率"问题的唯一正解：不要要求用户迁移，要寄生在用户已有的门面上。**

## 7. 待决策项清单（需发起人拍板）

| 编号 | 决策 | 选项 | 权衡 | 本报告建议 |
|---|---|---|---|---|
| **D1** | 核心层语言 | C++ / Rust / 纯 Kotlin | C++ 人才可得性高但内存安全风险高且易误用实验性 C++ interop；Rust 边界更安全、构建更一致但需学习投入；纯 Kotlin 风险最低但性能宣称站不住 | **若团队无既有 C++ 资产 → Rust；有则 C++ 并明令禁用实验性 C++ interop。** 更关键的是：**先冻结 C ABI 与格式规范，把语言决策降级为"2 周内可替换的实现细节"**，用 P0 的三组 Spike 实测后再定 |
| **D2** | KMP 集成深度 | 纯 KMP API + Native 核心 / KMP 作为整个库的基础 / 混合 | 纯 KMP 纯洁但性能受限；Native 核心性能好但矩阵大 | **混合（方案 D）**：API 与策略层 KMP，引擎层 SPI，Android/iOS 用 Native，**JVM 桌面用纯 Kotlin**（直接砍掉 6 个 native 变体） |
| **D3** | 加密与合规默认值 | 明文 + 脱敏（默认） / 强制加密 / 可配置 | 强制加密 = 走向 Logan 模式并制造"安全剧场"；明文 + 脱敏 = 无锁定最强、威胁模型诚实 | **V1 默认明文 + 脱敏，加密仅预留格式字段与威胁模型文档。** 这是本报告最坚定的建议之一 |
| **D4** | 结构化格式 | JSON / Protobuf / FlatBuffers / 自定义 | 见 §3.7 | **自定义帧层 + Protobuf 载荷 + JSON 导出**；不用 FlatBuffers |
| **D5** | 分析工具形态 | 桌面应用 / CLI / 两者 | GUI 体验好但成本高，且 V1 用户只有开发者 | **V1：规范 + CLI + Python 二次实现（必做）；GUI 放 V2** |
| **D6** | OTel 集成深度 | 仅导出 / 完整 SDK 集成 | SDK 集成会把依赖与体积风险强加给所有用户 | **V1 仅语义映射 + TraceContextProvider SPI；V2 提供独立可选导出 artifact** |
| **D7** | 脱敏机制与默认值 | 声明式优先 / 正则兜底 / 全量扫描 | 全量扫描开销大且误伤高；纯声明式覆盖不到自由文本 | **声明式字段（必做、默认开）+ 自由文本启发式（默认开但仅覆盖自由文本、有快速预筛）+ 严格模式（opt-in）**；另加编译期 Lint 覆盖"间接数据流"这一最大泄漏形态 |
| **D8** | 平台矩阵（V1） | 含/不含 Windows、桌面 JVM、Flutter、Web | 每多一个目标，产物变体与验证成本近线性增长 | **V1：Android + iOS + JVM（JVM 不带 native）。砍掉 Flutter、Web、Windows native** |
| **D9** | minSdk 与版本基线 | 21 / 24 / 更高 | minSdk 21 收益已很小，但承诺了就要测 | 建议**与脚手架对齐取 24**（除非有明确的 21–23 用户需求）；同时明确 Kotlin/AGP/Gradle/NDK/Xcode 的支持矩阵 |
| **D10** | 成功标准 | 自用为主 / 追求 OSS 采用 | 目标决定范围与节奏，二者混用会导致范围失控 | **以"自用生产可用"为第一验收标准，OSS 采用为加分项**。若要追求采用，则必须优先做桥接与脱敏模块（见 §4.2） |

## 附录 B：基准测量协议（防"自证清白"式作弊）

1. **测量面分离**：分别报告"API 侧延迟"（业务线程可见成本）与"落盘吞吐"（后台线程能力），不得混为一个数字；
2. **报分布，不报均值**：至少给出 P50 / P99 / P99.9 与最大值；
3. **固定变量**：同机型、同包名、同构建类型（release）、关闭调试器、飞行模式、清空后台、电量与温控状态说明；
4. **对比对象明确**：至少包含 `android.util.Log`、一个纯 Kotlin JVM 实现、以及（尽可能）XLog/Logan/MXLogger 的可构建版本；
5. **公布原始数据与脚本**，并给出机型清单；
6. **主动声明退化场景**（如低端机、磁盘接近写满、压缩级别提高时），这是可信度的来源；
7. 每次发布大版本时重跑基准并对比历史（性能回归等同于功能回归）。

## 附录 C：本报告的假设与待核实项

1. 3.4% / 49.3% / 69.7% / 30.3% 等数据来自滑铁卢大学 2025 年研究，样本为 Google Play 全球应用；中国区生态（应用分发渠道差异）下结论是否同构，需另行判断；
2. 货拉拉 Glog 的仓库地址、实际维护状态与文档完整度需以来源仓库为准（本次检索仅取得二手介绍）；
3. barK / WeKoiLog / ALog 等 2026 年新库的信息以仓库 README 与发布时间为准（例如 [WeKoiLog 介绍](https://tech.wekoi.cn/2026/01/28/wekoilog-ji-yu-mmap-de-gao-xing-neng-android-ri-zhi-ku/)）；
4. Kotlin C/ObjC 互操作的 Beta 状态存在时效性，需在 P0 复核官方稳定性文档；
5. AGP 9.x 与 KMP 的兼容矩阵、Kotlin 2.2.x 与 2.4.x 的取舍需实测确认（脚手架当前为 Kotlin 2.2.10，而官方文档站为 2.4.20）；
6. "XLog 是否有活跃社区 fork"未做穷尽检索，若有活跃 fork 则应重估 D11。
