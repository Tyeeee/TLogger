# 开源日志库横向对比与借鉴清单

> 这份文档回答一个问题：**别人已经做了什么、做得好的地方是什么、做得差的地方是什么，我们该抄哪些、该改哪些。**
>
> 写法尽量说人话。数据来源是真实查的（GitHub 官方接口的星星数、最后一次更新时间、许可证，以及公共软件仓库的实际检索），**查询时间：2026 年 9 月**。
> 凡是查不到、资料不足的，我直接写"没查到"，不猜。

---

## 第一章 一张总表看懂全局

**说明几个词：**
- **门面** = 只管"怎么调用、打印成什么样子"，不管日志存到哪。
- **落盘** = 真的把日志写到硬盘上长期保存。
- **内存映射** = 把硬盘上的文件"摊在桌上"直接写，比"写好纸条再交给管家放进抽屉"快得多。下面会反复出现。
- **公共仓库** = 安卓/Java 世界的"应用商店"（Maven Central）。发不上去，用户就只能拷源码，等于劝退。
- **维护状态** = 按最后一次更新时间分：半年内算活跃，半年到两年算放缓，超过两年算停滞。

### 1.1 门面型（只管打印，不管存储）

| 库 | 星星 | 最后更新 | 状态 | 最大优点 | 最大毛病 |
|---|---|---|---|---|---|
| **Timber**（Square） | 10847 | 2026-09 | 活跃 | 插件式设计，一行代码就能改变全局输出行为；自动取类名当标签 | 不存硬盘；全局只有一个配置，两个库抢一个开关会互相覆盖 |
| **orhanobut/Logger** | 13837 | **2022-09** | **停滞** | 输出好看，开箱即用，JSON 自动排版 | **近四年没更新**；格式难改；不存硬盘。星星最多但已经没人维护 |
| **elvishew/xLog** | 3340 | 2024-07 | 放缓 | 输出格式可定制性极强，支持打印到文件 | 不是内存映射，性能一般；近两年没更新 |
| **KLog** | 小 | — | 放缓 | 简单直接 | 功能单一 |

**注意重名**：安卓圈有两个"xLog"。一个是上面这个打印工具（elvishew/xLog），另一个是**腾讯的 XLog**（微信用的那套底层落盘库）。你调研表里写的是腾讯那个，别搞混。

### 1.2 落盘型（真正把日志写到硬盘长期保存）

| 库 | 星星 | 最后更新 | 状态 | 最大优点 | 最大毛病 |
|---|---|---|---|---|---|

| **ALog** | **没查到仓库** | — | — | 听说按天分文件、分块压缩 | **资料不足** |
| **WeKoiLog** | **没查到仓库** | — | — | 2026 年 1 月才发布 | **资料不足，社区几乎为零** |

## 第二章 从横向对比里看出来的"通病"

单个库的毛病叫毛病；**一类库反复出现的毛病叫通病**。通病才是我们要下手的地方——因为把通病治好，就是我们的产品。

### 2.1 门面型的通病

1. **只打印不存储**。程序关了日志就没了，出了线上问题查不到。
2. **全局只有一个配置**。这是最被低估的毛病：你的日志库和第三方 SDK 各设一次，后设的把先设的覆盖掉，排查起来极其头疼。
3. **格式想改改不动**。
4. **对隐私完全不负责**。谁都不管你往日志里写了什么。

### 2.2 落盘型的通病

1. **要连他家服务器才能看**（Logan）。这就是"上锁"。
2. **发不到公共仓库**（腾讯 XLog、Log4a、MXLogger 都不是标准公共仓库分发）。用户接入成本高，等于自我劝退。
3. **加密写死、不让选**。默认安全没错，但不该不让人关。
4. **停更**（Log4a 六年半、Logger 近四年）。而且停更的方式往往是"悄悄不更新"，用户不知道还能不能用。
5. **只支持安卓**。
6. **没有独立的查看工具**，或者工具还得配密钥。
7. **文档和格式说明太少**。用户想自己写个解析工具都写不出来。
8. **包体积大**，一上来全给你，没法只挑一部分。

### 2.3 跨平台型的通病

1. **只做门面不做存储**（Kermit、Napier）——跨平台了，但没解决真正的问题。
2. **一做存储就退化成"缓冲写文件"**（kmp-logcat）——先攒在内存里、过一会儿再写盘。这样做的后果是：**程序被系统杀掉的时候，攒着还没写的那部分就没了**。这恰恰是查线上崩溃时最需要的那几行日志。
3. **社区极小**。这几个库的星星数都在两位数，意味着几乎没有"别人踩过的坑"可以借。

### 2.4 老框架的通病

包大、慢、配置复杂、跟安卓环境不合拍。基本不用考虑。

## 第三章 逐个拆解：抄什么、改什么

### 3.1 Timber（门面标杆）

**是什么**：只管调用和分发，不管存哪。你可以自己插一个"树枝"进去接住日志。

**抄什么**
- **插件式设计**：让"输出到哪"变成可插拔的。我们的落盘引擎就应该做成一个可替换的"输出端"。
- **自动取类名当标签**：开发者不用手写标签，一行都省。

**改什么**
- 它全局只有一个配置，两个库抢一个开关会互相覆盖 → **我们做成多实例**：谁建的日志器归谁管，互不干扰。
- 它不落盘 → 我们落盘，并且是"撑得过进程被杀"的那种。

**关键结论**：**不要跟 Timber 抢位置，给它写个对接件挂上去。** 用户一行代码都不用改就能用上我们的存储能力。

### 3.2 orhanobut/Logger（反面教材）

**是什么**：输出好看，很多人用过，13837 颗星。

**抄什么**：开箱即用的体验、漂亮的排版。

**改什么**：**它 2022 年 9 月之后就没更新了。** 这是最典型的"星星多但已经死了"的例子。

**对我们的教训**：星星数不等于健康度。**所以我们从一开始就要公开"支持哪些版本、多久发一次版"**，并且在真的做不动的时候主动说"进入维护模式"，而不是悄悄消失。

### 3.3 elvishew/xLog（输出格式可定制）

**抄什么**：输出格式的高度可定制性（时间、线程、堆栈行数这些都能配）。

**改什么**：它不落盘、不是内存映射、2024 年之后放缓。

### 3.4 kmp-logcat（**最需要认真研究的一个**）

**是什么**：一个人写的跨平台日志库，功能比它的星星数看起来强得多。

**它的能力清单（这是它厉害的地方）**
- 跨平台，安卓 + 苹果都能用
- **惰性求值**：日志内容只在真的要输出时才拼字符串。这是个关键优化——如果这条日志被过滤掉了，拼字符串的功夫就白费了
- **能落盘**：带缓冲、按大小轮转、按时间清理、还能根据手机剩余空间动态调整文件上限
- **可以同时装多个日志器**（这就避开了 Timber 那个"全局配置打架"的毛病）
- **带了一个编译期检查**：如果你在代码里直接用了安卓自带的日志接口，它会报错，提示你改用它的接口
- **在苹果上默认把日志标记为"私密"**：苹果系统自己就有隐私标记机制，它用上了
- **发到了公共仓库**，Apache-2.0 许可，Kotlin 2.2.21
- 接口的命名和设计参考了 square/logcat 和 orhanobut/logger

**它的毛病（也就是我们的机会）**
1. **落盘不是内存映射**：它是"攒在内存里再写盘"。程序被杀掉，攒着的那部分就丢了——**而程序被杀的那一刻，恰恰是你最需要日志的时候**。
2. **只有系统级的隐私标记，没有真正的打码**：苹果那个"私密标记"只是让系统日志里不显示内容，日志文件里是什么还是什么。
3. **没有独立的查看工具，格式说明也不公开**：日志文件是它自己的格式，你不用它的库就读不了。
4. **没有压缩**：文件占地方。
5. **星星只有 8 个**，说明几乎没人验证过。
6. **没有结构化**：日志就是一整句话，机器不好处理。

**它给我们最大的启示**：**"编译期检查"这个想法不是我们独创的，已经有人做了，而且证明是可行的。** 所以我们不能把"有编译期检查"当卖点，真正能当卖点的是**它检查的是"有没有绕开我"，而我们检查的是"有没有把用户隐私写进日志"**——这两件事完全不是一个层次。

### 3.5 Kermit / Napier（跨平台门面）

**抄什么**：跨平台门面的接口设计、跟各平台原生输出通道的对接方式。

**改什么**：它们都不落盘。

**关键结论**：**给它们写对接件。** 让用 Kermit 的人把输出接到我们的存储引擎上——一行代码，用户不用换工具。

### 3.6 腾讯 XLog（mars 项目里的）

**先更正一条**：你的调研写"2018 年后实质弃养"，**这个说法不准确**。我查了官方接口：整个 mars 项目最后一次更新是 **2025 年 9 月**，17660 颗星，没有归档。准确的说法是"**最近一年没有更新**"，不是"弃养八年"。

这个更正很重要，因为它影响选型判断：一个还在维护的项目和一个死了八年的项目，处理方式完全不同。

**抄什么**
1. **文件开头写清楚"这是什么文件、第几版、怎么压缩加密的"**——这是"不上锁"最起码的要求。
2. **按天/按大小切文件**，再加"总大小上限 + 最多留几天"两道保险。
3. **配了一个独立的 Python 解码脚本**——这是我认为整个行业最值得抄的一招。它等于在说"我的格式写得足够清楚，清楚到能用另一种语言重写一遍"。
4. **随包附带代码混淆配置**，用户不用额外折腾。
5. **内存映射 + 撑过进程被杀**：这是它的核心价值，也是 Log4a 那组测速数据证明的东西（见第五章）。

**改什么**
1. **没发到公共仓库**（我直接去公共仓库目录查了，找不到）。用户只能拷源码用——这是它没有大规模普及的主要原因之一。
2. **只支持两种手机芯片**，模拟器等场景不方便。
3. **加密跟固定密钥绑在一起**：既不算真安全，也没得选。

### 3.7 美团 Logan

**抄什么**
1. **一整套闭环思路**：采集 → 切片 → 上传 → 服务端解析 → 定位问题。我们虽然不做平台，但**要给出出口**：能批量导出、能接到任意后端去。
2. **有人长期维护**（最后一次更新 2026 年 1 月）。这是它相对腾讯 XLog 最大的优势，也是我们最缺的东西。
3. 端上处理大日志的工程经验（怎么切片、怎么压缩）。

**改什么**
1. **必须搭他家服务器才能解密**——这是"上锁"的教科书案例。**我们的解码工具必须在完全没有我们服务的情况下也能用。**
2. **强制加密、不能关。**

### 3.8 MXLogger

**抄什么**
1. **一套 C/C++ 核心，多端复用**——这跟我们想做的事结构一样。它证明了**这种路子在个人开发者手里确实跑得通**，对我们是个正面证据。
2. 存储和序列化分得比较清楚。
3. 它还在更新（2026 年 9 月）。

**改什么**
1. **社区小**（163 星），出问题没人一起扛。
2. **它用的那种表格格式（FlatBuffers）在我们场景里是浪费**：那种格式是为"随便跳着读某一条"设计的，而我们是"一直往后追加、从头往后读"，好处用不上，却要多背一套工具。
3. **加密方式不检查内容有没有被改过**。以后我们真要做加密，得重新选。

### 3.9 货拉拉 Glog / ALog / WeKoiLog

**结论：资料不足，不建议写进对比表。**

我尝试找它们的代码仓库，没找到（GitHub 的搜索接口在这个环境里返回不了结果，我改用直接查询仓库地址的方式，也没命中）。

**处理建议**：
- 不要在正式对比文档里给它们打分或排名；
- 不要拿它们做性能对标（你没法跑，就没法验证）；
- 如果以后找到了，再补进来。

你调研表里说的"同步/异步双模式"这个设计**本身是值得采纳的**，我把它放进第四章的借鉴清单里（不管它是不是这个库原创的）。

## 第四章 借鉴清单：12 条必须补上的不足

这张表是整份文档的核心。左边是"别人没做好的"，右边是"我们打算怎么做"，最后是"怎么证明我们真做到了"。

| # | 别人没做好的 | 我们怎么做 | 怎么验证 |
|---|---|---|---|
| 1 | **程序被杀就丢日志**（所有"缓冲写文件"的方案） | 用内存映射：日记本直接摊在桌上写，程序死了内容还在 | 写一堆日志后直接杀进程，重启后能读回来 |
| 2 | **要连他家服务器才能看日志**（Logan） | 格式完全公开 + 官方解码器 + **用 Python 再独立写一个解码器** | 如果不用看我们的源码就能解码，说明格式真的公开了 |
| 3 | **发不到公共仓库**（腾讯 XLog、Log4a、MXLogger） | 必须上公共仓库，而且用户只写一行依赖就能用 | 全新项目、干净环境，只写一行依赖跑通三端 |
| 4 | **全局配置打架**（Timber、Logger） | 做成多实例，谁建的归谁管 | 同时开两个日志器互不干扰 |
| 5 | **隐私裸奔**（几乎全部） | 两条腿：给字段打标记自动打码 + 写代码时就检查 | 公开测试素材上，该抓的抓到 99%、抓错不超过 5% |
| 6 | **只在安卓能用**（落盘型全部） | 安卓、苹果、电脑三端 | 三端各跑一个示范工程 |
| 7 | **时间记录不可靠**（基本没人处理好） | 同时记"精确流逝时间"和"墙上时钟"，时钟被改动也记下来 | 手动改系统时间，日志顺序不乱 |
| 8 | **悄悄停更**（Log4a、Logger） | 公开"支持哪些版本、多久发一次版"，做不动了主动说 | 文档里能查到支持矩阵和发布节奏 |
| 9 | **包体积大、没法只拿一部分** | 拆成多个小包：核心接口 / 落盘 / 打码 / 检查插件 / 各种对接件 | 只要核心接口时不引入落盘和打码的代码 |
| 10 | **逼用户换工具**（所有库的通病） | 给 Timber、SLF4J、swift-log、Kermit 都写对接件 | 用户改一行就能接入 |
| 11 | **崩溃或断电后文件损坏** | 每条记录带校验；读到坏的地方能往后跳；**丢了多少必须报数** | 故意制造 1000 次崩溃，一条都不许悄悄丢 |
| 12 | **文档少、格式说不清**（MXLogger、Glog） | 格式说明和文档是一等交付物，不是附赠品 | 别人照着文档能自己写一个解码器 |

## 第五章 真实可查的性能数据

我在 Log4a 的文档里找到一组公开测速，值得贴出来看——**因为它是少见的、把"各种做法"放在同一台设备上比的数据**。

测试内容：在 Google Pixel 上写 **1 万条日志**。

| 做法 | 耗时 | 数据完整吗 | 落盘了吗 | 进程被杀后还在吗 |
|---|---|---|---|---|
| 纯写内存 | 13 毫秒 | 完整 | 没有 | **没了** |
| **Log4a（内存映射）** | **50 毫秒** | 完整 | 是 | **还在** |
| 缓冲写文件 | 61 毫秒 | 完整 | 是 | **没了** |
| **安卓自带日志** | **184 毫秒** | **没写完** | 没有 | 没了 |
| 不缓冲直接写文件 | 272 毫秒 | 完整 | 是 | 还在 |

**这组数据说明三件事**：

1. **内存映射大约是安卓自带日志的 3.7 倍快**，而且是在保证"进程被杀也不丢"的前提下。
2. **安卓自带日志那条路，连 1 万条都没记完**（表里写的是"没写完"）。因为它每写一条都要跨进程送给系统，有固定开销，系统还会限流。**这就是"自己写文件"仍然有价值的原因。**
3. **"缓冲写文件"看起来只慢一点点，代价却是"被杀就丢"**——而这恰恰是最贵的那部分日志。

**两个必须说清楚的限制**：
- 这是别人在 2018 年前后的设备上测的，只能当参考。
- **我们自己的性能数字必须自己重新测**，而且要按附录那套方法测（分开报两个数、报分布不报平均、公开原始数据）。

## 第六章 竞争压力：谁最可能吃掉我们的差异化

这一节不太舒服，但必须写。

把我们想做的四件事拆开看，**已经有别人做到几成了**：

| 我们想做的 | 谁已经做到了 | 我们还剩什么 |
|---|---|---|
| 跨平台一套接口 | Kermit、Napier、kmp-logcat（都做到了） | 没什么剩的，这是及格线不是卖点 |
| 能落盘 | kmp-logcat、Log4a、腾讯 XLog | 剩"内存映射 + 撑过被杀"这一点，kmp-logcat 没做到 |
| 编译期检查 | **kmp-logcat 已经带了** | 剩"检查的内容不同"：它查"你有没有绕开我"，我们查"你有没有把隐私写进日志" |
| 自动打码 | **没人在做** | **这一块最干净** |
| 格式公开 + 独立解码 | 腾讯 XLog 有一半（有 Python 脚本，但没发公共仓库、加密绑死） | 剩"发到公共仓库 + 完全不加密也能解 + 有独立 CLI" |
| 一次搞齐上面所有 | **没人做到** | 我们的位置就在这 |

**最需要警惕的一件事**：如果 kmp-logcat 的作者哪天加上了打码和内存映射，我们想做的事基本就被覆盖了。它现在只有 8 颗星，但它已经在公共仓库上、已经在更新、已经想清楚要做编译期检查。

**所以我们的护城河只能是这三样**（按牢固程度排）：
1. **打码的深度**（尤其是"数据转了几手才被写进日志"这种情况的处理——运行时抓不到，得靠编译期检查）
2. **格式公开且可验证**（规范 + 样本 + 独立实现，这是别人懒得做、但最难抄的）
3. **落盘可靠性**（撑得过进程被杀，且崩溃后数据不坏）

## 第七章 对你那套架构的启发（和 Router 放在一起看）

你现在做的是"一套架构，里面很多独立组件"，Router 先做，日志接上。那日志组件就不能只看自己，得跟整套架构合拍。

### 7.1 跟 Router 那套应该保持一致的六条约定

| 约定 | 为什么 |
|---|---|
| **能用编译期解决的，不放到运行期** | Router 走的是编译期生成这套思路，日志这边就是"写代码时就检查隐私泄漏"。整套架构风格统一，用户学一次就懂 |
| **不做全局单例** | 组件化架构里最怕互相覆盖配置。日志器必须是谁建归谁管 |
| **每个组件独立发布、独立版本** | Router 和日志不能绑在一个版本号上，不然改一个要升两个 |
| **可裁剪** | 用户如果只想要打码、不想要日志库，也得能单独拿走 |
| **初始化时机明确** | 谁先谁后要写清楚，不能靠"反正它会自己初始化" |
| **降级要说清楚** | 硬盘满了、没权限了，日志组件该退回什么状态，要写在文档里，不能悄悄失灵 |

### 7.2 建议拆成几个包（这样"体积大"这个通病就解决了）

| 包 | 里面是什么 | 谁需要 |
|---|---|---|
| 核心接口 | 只管"怎么调用"，不含任何存储实现 | 所有人 |
| 落盘引擎（安卓 / 苹果 / 电脑各一份） | 真正写文件的那部分 | 需要存日志的人 |
| 打码 | 敏感信息识别和替换 | 关心隐私的人（**可以单独用**） |
| 检查插件 | 写代码时的检查 | 所有人（改个构建配置就行） |
| 各种对接件 | 挂到 Timber / SLF4J / swift-log / Kermit 上 | 不想换工具的人 |
| 查看工具 | 命令行解码 | 要看日志的人 |

**关键点**：用户要"打码"这一样，就只拿"打码"这一个包，不用被迫装一整套。这正是现有那些库最被诟病的地方（要么全拿，要么没有）。

### 7.3 跟 Router 可能的协同点

- **共用一套编译期基础设施**：Router 用的代码生成工具（KSP）和日志的检查插件可以共用一套配置和版本，用户不用装两套。
- **初始化顺序**：Router 通常在启动早期就要用，日志也是。谁先谁后要定死，最好由架构层统一编排，而不是各组件自己抢。
- **多进程**：组件化架构里经常有多个进程。日志组件要明确支持"每个进程自己一份日志文件"，这是现有落盘库普遍做不好的地方。

## 最后：这份对比给我们的三个结论

1. **"跨平台 + 能落盘"已经不是空白了**（kmp-logcat 做到了），不能当卖点；**"自动打码"仍然是空白**，而且是最干净的一块。
2. **我们真正该抄的招数是"格式公开 + 独立解码"**（腾讯 XLog 的 Python 脚本证明了它有效），该改的毛病是"发不到公共仓库、要连服务端、加密绑死"。
3. **最重要的不是功能比别人多，而是承诺比别人可靠**：现有库最大的问题不是做得少，是**做着做着就没人管了、或者悄悄上了锁**。一个公开支持矩阵、按时发版、格式永不上锁的日志库，在这个圈子里本身就是稀缺品。
