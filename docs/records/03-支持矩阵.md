## 二、为什么是这些（理由）

**为什么跟着项目走，而不是跟着官方最新走？**
因为现在这个库的第一使用者是**你自己**（外部用户还在验证阶段）。项目用什么，库就用什么，能省掉大量版本兼容的排查。等真有外部用户提出诉求，再谈放宽。

**为什么 JVM 目标取 11 而不是 17？**
TRouter 的 `trouter-core` 用的是 11。同一个仓库里混用两套目标版本，会在排查编译问题时制造额外的噪音。**保持一致比追新重要。**
（例外：将来做编译期检查的模块要用 17，因为安卓的检查工具自身要求 17——TRouter 的 `trouter-lint` 就是这么处理的。）

**为什么最低安卓版本取 24？**
项目本身是 24（原本的文档里写的是 21，与实际不符）。24 之上的适配成本更低，而且不需要为老系统做额外的兼容分支。**承诺了就要测，所以宁可承诺小一点。**

## 三、苹果端：暂不列入支持矩阵

**原因**：本机只装了 Command Line Tools，**没有 Xcode**，苹果产物现在编不出来，也就无法验证。

代码层面已经准备好了——共用代码写在 `src/commonMain/`，不碰 JVM 专有 API；`TLogger/build.gradle.kts` 里预留了目标位置。装上 Xcode 后补三行即可开启。

**一旦开启，这张表必须补上**：最低支持的苹果系统版本。
（参考教训：kmp-logcat **没有**在库里声明最低苹果系统版本，只有演示 App 声明了——用户可能在老系统上踩坑。这是我们要避开的错。）

## 四、风险与待确认

| 风险 | 影响 | 怎么处理 |
|---|---|---|
| **Kotlin 2.2.10 与 Gradle 9.5 的组合** | 官方对"Kotlin 版本 × Gradle 版本"有兼容范围。2.2.10 发布于 Gradle 9.5 之前，跨平台插件可能报不兼容警告甚至失败 | **第 1 周的构建验证会直接给出答案**。失败的话有两个选择：升 Kotlin，或降 Gradle |
| **AGP 9.3.0 + 跨平台库插件的组合** | 这是 AGP 9 起的新写法（`com.android.kotlin.multiplatform.library`），比老的 `com.android.library` + KMP 更新，踩坑的人少 | 同上，构建验证给出答案 |
| 项目与 TRouter 的 AGP 小版本不一致（9.3.0 / 9.3.2） | 两边不共享构建逻辑时不构成问题 | 若将来抽出公共构建脚本，再统一 |
| 安卓 Studio 会重新生成 `gradle-daemon-jvm.properties` | 那个文件要求 JDK 25，本机没有，会触发下载 | 已删除；若被重新生成，再删一次。**如果将来定下要用 JDK 25，这张表也要改** |
| 编译期检查模块会要求 JVM 17 | 与主模块的 11 不一致，容易困惑 | 已记录理由（检查工具自身要求 17），写进文档说明 |

## 五、这张表怎么对外说

对外只承诺一件事：**"这张表里的组合我们测过"**——不承诺表外的组合，也不说"兼容所有版本"。

具体做法（对应约束 15"公开支持矩阵和发布节奏"）：

1. 表里的组合进自动构建矩阵，定期跑。
2. 表外的组合收到问题时："先升级到表内组合，如果还不行我们再查"。
3. **每次发布都在发布说明里重述这张表**，不要让人去翻历史文档。
