# 日志组件 · 架构设计约束（开工依据）

> 这份文档是**开工前必须定死的规矩**。
>
> 它把横向对比得出的"12 条必须补上的不足"、源码体检新发现的 4 条、构建配置分析发现的 1 条、以及"第一使用者是外部用户"这个定案带来的 2 条，一共 **19 条**，翻译成"代码该怎么写"。
> 每一条都带四样东西：**为什么这么定 / 落在哪个模块 / 违反了会怎样 / 怎么验收**。
>
> **用法规矩：以后写代码时，任何一条约束都不能靠"这次先这样"绕过。绕过就要改这篇文档，而且要写下理由。**

---

## 第 0 章 这个组件在整套架构里的位置

你在搭的是一套"一个架构 + 很多独立组件"的东西：Router 先做，日志接上，后面还会有别的。

所以日志组件不能只顾自己好用，得跟整套架构合拍。

### 0.1 跟 Router 那套保持一致的六条通用约定

这六条不只管日志，是整套架构的规矩，日志组件必须遵守：

| 约定 | 说明 |
|---|---|
| **能用编译期解决的，不放到运行期** | Router 走的是"编译期生成代码"这条路，日志这边对应的是"写代码时就检查隐私泄漏"。风格统一，用户学一次就懂 |
| **不做全局单例** | 组件化架构最怕互相覆盖配置。任何组件都不许偷偷改全局状态 |
| **每个组件独立发布、独立版本** | Router 和日志不能绑在同一个版本号上，改一个不用升另一个 |
| **可裁剪** | 用户要哪块就拿哪块，不许"要么全拿要么没有" |
| **初始化时机明确** | 谁先谁后写清楚，不许靠"反正它会自己初始化" |
| **降级要说清楚** | 出错时退回什么状态要写进文档，不许悄悄失灵 |

### 0.2 组件之间的依赖方向

一句话铁律：**所有人都可以依赖"接口层"，但没有任何人能依赖"别人的实现"。**

- 日志组件可以被 Router 依赖（Router 要打日志），但日志组件**不许依赖 Router**。
- 日志组件的各个子模块之间，也只能向"核心接口"这一个方向依赖。

这条规矩看起来死板，但它决定了以后能不能单独升级、单独替换、单独裁剪。

## 第 1 章 模块划分与依赖方向

### 1.1 拆成十二个包

**注意"第几版"这一列**——第一版只做输出链路，落盘整体推到第二版（原因见主报告：日常用不到）。

| 模块 | 它负责什么 | 第几版 | 允许依赖 | 绝对不许依赖 | 体积预算 |
|---|---|---|---|---|---|
| **log-core** | 对外接口、日志级别、事件定义、SPI 插座、**来源维度** | 第一版 | 只有 Kotlin 标准库 | 任何平台 IO | ≤ 80KB |
| **log-context** | 链路号、会话号、版本号、账号上下文；**跨协程/线程自动传递** | 第一版 | core | 任何引擎 | ≤ 40KB |
| **log-output-android** | 安卓输出通道（系统日志） | 第一版 | core | 引擎、打码、对接件 | ≤ 60KB |
| **log-output-apple** | 苹果输出通道 | 第一版 | core | 同上 | ≤ 60KB |
| **log-ring** | 最近 N 条的环形缓冲 + 导成文本 | 第一版 | core | 引擎 | ≤ 80KB |
| **log-redact** | 敏感信息识别、替换、审计报告。**必须能脱离日志库单独使用** | 第一版 | core（只需要极少接口） | 任何引擎 | ≤ 200KB |
| **log-lint** | 写代码时的检查（编译期）。**只发 Gradle 插件/lint 包，不进运行时** | 第一版 | 无运行时依赖 | 所有运行时模块 | 不计入 App 体积 |
| **log-bridge-xxx** | 挂到 Timber / SLF4J / swift-log / Kermit 上的对接件，一个对接件一个包 | 第一版 | core + 对方门面 | 引擎实现 | 每个 ≤ 20KB |
| **log-engine-android** | 安卓上真正写文件的那部分（内存映射） | **第二版** | core | 打码、检查插件、对接件 | ≤ 400KB（含压缩） |
| **log-engine-apple** | 苹果上写文件的那部分 | **第二版** | core | 同上 | ≤ 1.2MB |
| **log-engine-jvm** | 电脑上的纯 Kotlin 版本（不带底层加速） | **第二版** | core | 同上 | ≤ 150KB |
| **log-tool** | 命令行查看工具（解码、导出、统计、校验） | **第二版** | 格式规范（不是引擎代码） | 所有 App 侧模块 | 独立发布 |

### 1.2 四条依赖铁律

1. **log-core 里不许出现任何 `File`、`open`、`write`、`mmap` 相关的东西。** 它只定义"日志长什么样""往哪送"。
2. **log-redact 必须能单独被别人拿走用。** 如果一个项目只想用打码、不想用我们的日志库，他应该能只依赖 log-redact。这条是"打码作为敲门砖"战略的物理基础，破了这条战略就废了。
3. **对接件不许依赖引擎实现。** 对接件只认识 core 的插座，换引擎不该影响对接件。
4. **输出链路不许依赖落盘引擎。** 第一版的输出通道、上下文、环形缓冲都不许引用引擎模块——**这样第一版可以完全不装引擎就跑起来**，第二版接上引擎时用户代码一行都不用改。这条是第一版能不能独立交付的关键。

### 1.3 为什么这么拆

现有那些库最被诟病的地方就是"要么全拿要么没有、包体积大"。这么拆之后：

- 只要"写代码时检查"→ 只装 log-lint（不进 App，零体积）
- 只要"打码"→ 只装 log-redact
- 要完整能力 → 装 core + 对应平台的 engine
- 已经在用 Timber → 装 core + engine + bridge-timber

## 第 2 章 19 条硬约束

前 12 条来自横向对比（"别人没做好的"），第 13–16 条来自 kmp-logcat 的源码体检，第 17 条来自它的构建配置分析，**第 18–19 条来自"第一使用者是外部用户"这个定案**（见第 8 章）。

### A 组：存储与可靠性（1–5）

**约束 1 · 日志必须撑得过"程序被杀"**

- **为什么**：程序被杀的那一刻，恰恰是最需要日志的时候。所有"先攒在内存里、过一会儿再写盘"的方案，一被杀就把最关键的几行丢了（kmp-logcat 就是这个毛病）。
- **落在哪**：log-engine-*（安卓和苹果）+ 格式层。
- **违反了会怎样**：这个库最核心的价值就没了，跟做一个"好看点的打印工具"没区别。
- **怎么验收**：写一批日志 → 用系统命令直接杀掉进程 → 重启后必须能读回来，且丢失量在文档承诺的范围内。

**约束 2 · 硬盘满、文件被截断，都不许把程序弄崩**

- **为什么**：用"把文件摊在桌上写"的手法，硬盘满了不是报错，是**直接把程序干掉**（著名数据库 LevelDB 就栽过）。
- **落在哪**：log-engine-*。
- **违反了会怎样**：用户手机存储一满，你的日志库反而成了崩溃源——这是最不可接受的失败形态。
- **怎么验收**：人为制造 200 次"硬盘满 / 文件被切 / 内容被涂改"，程序一次都不许崩。

**约束 3 · 每条记录自带校验；坏的地方能跳过去；丢了多少必须报数**

- **为什么**：崩溃和掉电会让文件尾巴变成乱码。读的时候不能整份文件作废。
- **落在哪**：格式层 + log-engine-* + log-tool（读取端也要实现恢复逻辑）。
- **违反了会怎样**：一次意外让整份日志变成废纸。
- **怎么验收**：随机涂改文件字节，扫描时能跳过坏点继续读，并且**明确报出"丢弃了多少条"**——绝对不许静默丢数据。

**约束 4 · 一个进程一份文件，不做多进程共享**

- **为什么**：两个进程同时写一个文件，需要跨进程锁，复杂度和出错面都很大。组件化架构里多进程很常见（推送、后台服务各一个进程）。
- **落在哪**：log-engine-*。
- **违反了会怎样**：日志串行、文件损坏，而且极难复现。
- **怎么验收**：两个进程同时压测 8 小时，不打架、不串行、不损坏。

**约束 5 · 时间要记两套：精确流逝时间 + 墙上时钟**

- **为什么**：用户改系统时间、系统自动对时，都会让"墙上时钟"跳变。只记墙上时钟，日志顺序会乱，跨文件归并也会乱。这块几乎没人做好。
- **落在哪**：log-core（采集）+ log-engine-*（写入）+ log-tool（归并）。
- **违反了会怎样**：排障时时间线是错的，越查越乱。
- **怎么验收**：手动改系统时间、跨时区回放，日志顺序不乱。

### B 组：无锁定（6–8）

**约束 6 · 文件开头必须写清楚"这是什么文件"**

- **为什么**：文件自己要说清楚"我是谁、第几版、用什么压缩、时间基准是什么"。这是"不上锁"最起码的要求，也是以后能换实现的前提。
- **落在哪**：格式层（写） + log-tool（读）。
- **违反了会怎样**：以后改一次格式，旧日志就没人能读了。
- **怎么验收**：只拿一个日志文件给一个不懂我们代码的人，他能照着文件头知道这是什么、该用什么工具读。

**约束 7 · 格式要公开到"别人能用另一种语言重写一个解码器"**

- **为什么**：腾讯 XLog 配了一个独立 Python 脚本，这是整个行业最值得抄的一招。美团的方案必须搭服务器才能解密，这就是"上锁"。
- **落在哪**：文档 + log-tool + 一套独立实现。
- **违反了会怎样**：所谓"无锁定"就是口号。
- **怎么验收**：**用 Python 只依据文档、不看我们的源码，独立写一个解码器**，输出结果跟官方工具字节级一致。做不到，说明文档不够清楚。

**约束 8 · 必须发到公共软件仓库，用户只写一行依赖**

- **为什么**：腾讯 XLog、Log4a、MXLogger 都没发上去（我逐个查过），用户只能拷源码——这是它们没普及的主要原因之一。
- **落在哪**：发布流水线。
- **违反了会怎样**：接入成本高到没人愿意试。
- **怎么验收**：全新的空项目、干净的机器，只写一行依赖，三个平台各跑通一个示范。

### C 组：隐私（9–11）

**约束 9 · 打码分三层，最早的那层最重要**

- **为什么**：如果等日志拼成一句话再打码，敏感内容已经在内存里转了一圈。
- **三层分别是**：
  1. **字段标记**（最准，默认开）：开发者在定义日志字段时标一句"这是手机号"，值在**还没变成日志之前**就被处理掉。
  2. **自由文本扫描**（兜底，默认开）：对没法预判的文本扫一遍，但规则要少而精。
  3. **便宜预筛**：扫描前先看长度、字符集、校验位（比如银行卡号有校验规则），别一上来就做复杂判断。
- **落在哪**：第 1 层在 log-redact 的接口层；第 2、3 层在引擎里（落盘前）。
- **违反了会怎样**：打码要么没用，要么慢到用户关掉它。
- **怎么验收**：公开语料上"该抓的抓到 99%、抓错不超过 5%"，对速度的影响不超过 5%。

**约束 10 · 编译期检查必须查"隐私"，不是查"有没有用我的接口"**

- **为什么**：kmp-logcat 已经带了编译期检查，但它查的是"你有没有绕开我用安卓自带的日志"。那属于**排他性检查**，不是隐私检查。而研究发现，**62.5% 的泄漏是数据转了几手之后才被写进日志的**，运行时根本抓不到，只有编译期能抓。
- **落在哪**：log-lint。
- **怎么做到**：不要一上来做全程序复杂分析。研究发现泄漏路径通常只有 **2 到 4 句话、而且多半在同一个方法里**，所以做法是：
  1. 先标出"敏感数据的来源"（界面上用户输入的内容、设备标识、位置、通讯录、剪贴板、账号信息等）；
  2. 在**同一个方法内部**跟踪这些数据被赋值给谁；
  3. 一旦它们被传进任何日志接口（包括安卓自带的），报错并给出修改建议。
- **违反了会怎样**：我们就跟 kmp-logcat 撞在同一个层次上，没有差异化。
- **怎么验收**：在 3 个开源 App 上运行，误报不超过 10 条/项目；故意写的 20 个泄漏样例全部抓到。

**约束 11 · 用"换代号"代替"涂黑"，并且绝不说"合规"**

- **为什么**：全涂黑了就没法排障，用户会把打码关掉。换成代号（同一个手机号每次都换成同一个代号）既能对上号、又看不出内容。
- **同时**：打码是"降低风险"，**不等于"我们合规了"**。责任始终在 App 开发者身上。
- **落在哪**：log-redact + 全部对外文案。
- **违反了会怎样**：前者让功能被弃用，后者会招来真实的法律风险。
- **怎么验收**：文案审查（全文不许出现"通过某某合规"）；功能上验证"同一个值在不同日志里代号一致"。

### D 组：接口与兼容（12–14）

**约束 12 · 对外接口不许出现底层类型；跨语言只用最基础的接口**

- **为什么**：Kotlin 连接底层代码这条路，官方自己标的是**测试状态**，还跟开发工具版本绑得很紧。一旦把底层类型暴露到对外接口上，以后想换实现、想让用户升级，都会很痛。
- **落在哪**：全部对外 API。
- **违反了会怎样**：用户被"锁"在我们当前这个实现和版本组合上。
- **怎么验收**：对外 API 里搜不到任何底层类型；升级底层实现时，用户代码一行都不用改。

**约束 13 · 不做全局单例，多实例互不干扰**

- **为什么**：Timber、Logger 这些库都是全局一个配置，两个库抢一个开关会互相覆盖。
- **落在哪**：log-core。
- **违反了会怎样**：用户接了两个日志组件后行为诡异，而且极难排查。
- **怎么验收**：同时创建两个日志实例，配置互不影响；卸载其中一个，另一个正常工作。

**约束 14 · 每个模块能单独拿走**

- **为什么**：见 1.3。
- **怎么验收**：只依赖 log-redact 的示范工程里，编出来的包里搜不到引擎代码。

### E 组：承诺与可信度（15–16）

**约束 15 · 公开支持矩阵和发布节奏；做不动了主动说**

- **为什么**：现有库最大的问题不是功能少，是**做着做着没人管了**（Log4a 停了六年半、Logger 停了近四年），而且都是悄悄停的，用户不知道还能不能用。
- **落在哪**：文档 + 发布流程。
- **怎么验收**：文档里能查到"支持哪些版本、多久发一次版、出问题怎么找我们"。

**约束 16 · 性能数字必须可复现，而且要主动说"我们哪里不占优"**

- **为什么**：没有原始数据的性能宣传，被拆穿是迟早的事。
- **具体做法**：分开报"业务线程感知的耗时"和"落盘速度"；报分布不报平均；公开脚本、机型清单、原始数据；**主动写明什么情况下我们更慢**。
- **怎么验收**：随便一个第三方拿到我们的测速脚本，在同款机型上能跑出接近的数字。

### F 组：兼容性门槛（17）

**约束 17 · 必须有一道"对外接口兼容性门槛"** ★★★

- **为什么**：kmp-logcat 整个仓库**完全没有兼容性保护**——没有显式接口声明、没有接口快照文件、没有二进制兼容检查。意思是它**随时可能悄悄改坏用户的代码而自己不知道**。对一个"要被别人长期依赖的基础组件"来说，这是最不该缺的一块。
- **具体做三件事**：
  1. **打开显式接口声明**（构建配置里的 `explicitApi()`）：所有对外暴露的东西必须显式写清楚，避免"不小心把内部实现暴露出去"。
  2. **每次构建生成一份"对外接口快照"文件，并提交进仓库**：以后任何对外的改动，都会在代码评审里显示成一行行差异，改了什么一目了然。
  3. **破坏性改动必须升主版本号，并且附带迁移说明**。
- **落在哪**：log-core、log-redact，以及所有对外发布的模块。
- **违反了会怎样**：用户升级一个小版本就编译不过，从此不敢升级再升——这跟"承诺可靠"的定位直接矛盾。
- **怎么验收**：故意改一个对外方法的签名，构建必须失败并指出差异；同时本地手动发布不能受签名要求影响。

## 第 3 章 对外接口的冻结项

开工前要定死，之后**加功能可以，改这些要开版本**：

1. **不许暴露文件路径、缓冲区、指针、底层库的任何类型。**
2. **异步写入的"最多会丢多少"必须写进公开文档**（比如"异步模式下，进程异常终止最多丢失 N KB 以内的日志"）。不许含糊其辞。
3. **初始化必须显式**。不许"悄悄在第一次调用时自动初始化"，因为那样用户无法控制时机。
4. **关闭/释放语义要明确**：调用关闭之后，缓冲区的数据必须落盘完成才返回。
5. **失败必须可感知**：写入失败不许静默吞掉，要通过一个回调或状态暴露出来。
6. **降级行为要定义**：没权限、硬盘满、目录不存在时，日志组件应该变成什么状态（建议：退化成"只写系统日志 + 记录一个错误状态"，绝不抛异常给业务线程）。

## 第 4 章 构建与发布约束

### 4.1 版本矩阵要在第一阶段定死

现状是项目壳子用 Kotlin 2.2.10，官方最新是 2.4.20；文档里写的"AGP 8.0+"跟壳子实际的 AGP 9.3 也对不上。

必须明确并公开一张表：
**最低支持哪个 Kotlin、哪个安卓构建工具、哪个 Gradle、哪个 NDK、哪个苹果开发工具版本、最低安卓版本。**

参考：当前壳子实际是 Gradle 9.5 / AGP 9.3 / Kotlin 2.2.10 / 最低安卓 24；kmp-logcat 的选择是 Kotlin 2.2.21、最低安卓 24、JVM 目标 17。

### 4.2 电脑端不引入底层加速

这条是**减负的核心手段**：电脑上直接用纯 Kotlin 版本，能省掉为 Windows / Mac / Linux 各打一份底层库的六份产物。代价是电脑上慢一点，可以接受。

参考：kmp-logcat 甚至连 NDK 都没用（纯 Kotlin + 系统接口），这印证了"底层内核是性能选择，不是能力必需"。

### 4.3 苹果那边只做一种交付形态

- **第一版只服务 Kotlin 跨平台项目**：库通过公共仓库发 Kotlin 编译产物（klib）就行，用户在自己项目里打包时自动生成苹果用的包。**不做 XCFramework、不做 SPM、不做 CocoaPods。**
- 但有一件 must：**库本身必须声明"最低支持哪个苹果系统版本"**。kmp-logcat 犯了这个错——它的演示 App 声明了 18.2，**库本身却什么都没声明**，用户可能在老系统上踩坑。
- 另外：**自动流程里必须有一个"用户视角"的苹果示范工程真的编译链接一次**（见 4.5）。

### 4.4 编译期检查怎么发出去（照抄 kmp-logcat 的做法）

它的做法是最漂亮的一手，直接抄：

- 检查模块**不单独发布**，公共仓库里没有它的坐标。
- 通过构建配置里的 `lintPublish(...) { isTransitive = false }` **塞进库的 AAR 里**。
- 效果：**用户什么都不用配，装上库就自动有了检查。**（`isTransitive = false` 是为了不让检查工具的依赖污染用户的依赖表。）
- 注册做双保险：资源目录下的服务声明文件 + jar 包清单属性。

**唯一要当心的地方**：它把检查跟某个具体的 lint 版本绑死了（内部声明了"用当前版本的接口"），等于**用户必须用足够新的安卓构建工具，否则检查可能不生效**。这种隐性版本要求一定要写进文档，否则会变成高频求助。

### 4.5 必须进自动检查的几项

| 检查项 | 为什么 |
|---|---|
| 新手机"每页 16KB"的内存分页对齐 | 不检查的话，故障形态是老手机正常、新手机一启动就崩，极难查 |
| 三个平台的编译 + 单元测试 | — |
| **一个"用户视角"的示范工程（安卓、苹果各一个），苹果那个必须真的编译链接出包** | kmp-logcat 的自动流程**从来没链接过 framework**，所以"打包出来在用户项目里能不能用"它抓不到。这是跨平台库最常见、最晚发现的故障 |
| **对外接口快照比对** | 约束 17。防止悄悄改坏用户的代码 |
| 底层代码的随机输入撞击测试（跑一小会儿） | 底层崩溃面太大 |
| 包体积预算对比 | 超标就算性能回归 |
| 两条依赖铁律（core 不含 IO、redact 不依赖引擎） | 用脚本检查，靠人自觉一定会破 |
| **文档里的版本号与实际版本号一致性** | 抄它的同步脚本；并且补上它漏掉的一项——它还漏检了 README 里写死的 Kotlin 版本 |
| **真机测试要有一个定时跑的口子** | 它完全没有（真机测试只在本地手动跑）。我们不要求每次提交都跑，但必须有定时任务守着 |

### 4.6 发布相关

- **走公共仓库的新通道**（老通道已经停用）。
- **签名开关不许无条件打开**：它踩过这个坑——配置里写死了"启用签名"，导致本地想手动发个测试包时因为没密钥而失败。要用环境变量控制。
- **随包提供代码混淆配置**（consumer 规则），用户不用额外折腾。这条它做对了，值得抄。
- **编译期检查不发布运行时依赖**，用户零配置（见 4.4）。
- **底层库的符号要么保留、要么映射关系随发布一起提供**，否则用户线上崩溃没法还原。
- **发版任务必须跑在苹果机器上**（因为要出苹果产物），这一点它做对了。
- **版本号只在配置文件里出现一次**，文档里的版本由脚本自动校验，避免两处不一致。

## 第 5 章 隐私模块的专项约束

这一块法律风险最高，单独定规矩：

1. **能力边界必须写清楚**：我们能查什么、查不到什么。比如"经过 Base64 编码、URL 编码、或者自己拼接过之后的敏感数据，我们不保证能识别"。
2. **规则可关闭、可观测**：每条规则能单独关；命中多少次要有统计，用户能看见"今天打码了多少条"。
3. **必须出审计报告**：哪些字段被打码、命中哪条规则、有多少条，能导出。这既是排障依据，也是"我们做了处理"的记录。
4. **留存上限 + 一键清除**：日志文件必须有保存天数上限，并且提供一个"立刻清空所有日志"的接口——因为用户有删除权。
5. **用词规范**：对外只说"提供打码能力""降低泄漏风险"，**禁止**出现"通过 GDPR / 个人信息保护法合规"这类表述。
6. **责任边界要写进文档**：明确写着"日志内容是否合规，责任在 App 开发者，本库只提供工具"。
7. **脱敏映射表默认不落盘**：能让"代号还原成真值"的对照表，默认不写文件；开启时必须加密，并且要在文档里说明它本身就是敏感物。

### 8.2 补两条约束（因为第一使用者是"外部用户"）

**约束 18 · 不许假设使用者的架构长什么样** ★★★

- **为什么**：外部用户里**大多数没有组件化架构**（只有一个 app 模块）。如果我们的接口要求"每个模块都要注册来源身份"，他们第一步就卡住了——**我们最有价值的能力，目标用户里大部分用不上。**
- **怎么做**：
  - 来源维度**可选、由用户自己定义名字**；只有一个默认来源时，功能完全可用。
  - 我们的架构概念（路由协同、页面上下文）只作为**可选的加分能力**出现，不做任何依赖。
  - 对外主打的排序固定为：① 打码 → ② 链路串联 → ③ 零迁移对接件 → ④ 来源维度。
- **违反了会怎样**：产品变成"只对做了组件化的团队有用"，而这类人恰恰很少。
- **怎么验收**：一个只有单模块的普通 App，接入过程里**不出现"组件""模块"这类必须理解的概念**就能跑起来。

**约束 19 · 默认值保守、错误可感知** ★★

- **为什么**：陌生人的项目环境千奇百怪（没初始化、目录没权限、存储满、版本不匹配）。**任何"悄悄失灵"都会变成一条差评。**
- **怎么做**：
  - 默认不采集多余信息、默认打码开启、默认级别保守。
  - **没初始化不许崩**（最多是"什么都不打"），写失败/丢弃必须有可观测的出口（回调或状态），不许静默吞。
  - 版本不兼容要明确报错，不许静默降级。
- **违反了会怎样**：用户的第一次体验就是崩或者"日志没了但没人知道"。
- **怎么验收**：在"完全没初始化 / 存储满 / 目录无权限 / 版本不匹配"四种情况下，程序都不崩，而且都能从状态里看出发生了什么。

### 8.3 第一版的验收清单（在上面那批约束之外）

**输出端**（对应主报告第二阶段）：

- [ ] 一个开关能"只看某个来源"的日志
- [ ] 两个来源级别互不干扰，上层能一句话全部覆盖
- [ ] 10KB 长日志能完整显示（分段可拼回）
- [ ] 循环里打十万条不卡（惰性求值生效）
- [ ] 第三方 SDK 的日志能一键屏蔽
- [ ] **只有单模块的普通 App 能接入，且不被迫理解"组件"概念** → 约束 18
- [ ] 四种异常情况下都不崩且状态可见 → 约束 19

**链路与上下文**（第四阶段）：

- [ ] 一次操作跨 3 个来源的 5 条日志，一次过滤全出、顺序正确、中间零改动
- [ ] 环形缓冲存 2000 条、内存 ≤ 2MB、能导出成文本

## 最后一句

这份文档里最容易被忽略、但最重要的一条是**约束 15（主动公开承诺）**。

因为横向对比看下来，那些库失败的原因基本都不是"功能不够"，而是**说着要做、做着做着就没声了，或者悄悄上了锁**。

在一个大家都被"库突然不维护了"坑过的圈子里，**"承诺可靠"本身就是比功能更稀缺的东西**。
