# kmp-logcat 源码级体检报告

> **体检对象**：kmp-logcat（作者 Airsaid），一个跨平台（安卓 + 苹果）日志库，发在公共仓库上，Apache-2.0。
> **体检时间**：2026 年 9 月。
> **怎么查的**：把它的代码完整拉到本地，逐行读了核心运行时代码（入口、注册表、日志器、格式器、输出端、安卓/IOS 两套文件写入、编译期检查、C 接口包装文件），总共约 5300 行 Kotlin 里最关键的 1500 多行。
> **为什么值得花这个功夫**：它的星星只有 8 个，但功能清单说明它是**市面上离我们最近的一个**。二手介绍不可靠，必须看源码。

---

## 先说结论

读完源码后，我的判断比看 README 时**更分化**了：

- **它的"接口层设计"很成熟，明显借鉴过 Square 的成熟做法，这一层值得我们认真抄。**
- **它的"存储层"是脆的**：攒在内存里、过一会儿再写盘，程序被杀就丢；它试图用一个全局崩溃处理器来补救，但那个补丁救不了真正致命的场景。
- **它证明了两件对我们极其重要的事**（见第五章），其中一件**直接修正了我们之前的架构判断**。

一句话：**它的接口层是老师，存储层是反面教材。**

## 第一章 它的整体结构

它的结构比表面看起来清晰。用文字画出来是这样一条链：

```
用户代码
   ↓  调用 logcat { "消息" }        ← 入口，是个内联函数，消息是"惰性"的
全局注册表（LogcatLogger）          ← 一个进程级的列表，存着所有"日志器"
   ↓  遍历列表逐个投递
日志器（LogcatLogger 的实现）
   ├─ AndroidLogcatLogger           ← 只输出到系统日志
   ├─ IosLogcatLogger               ← 只输出到苹果系统日志
   ├─ PrintLogger                   ← 只打印（电脑上用）
   └─ DiskLogger                    ← 写文件（重点，也是它最弱的一环）
        ↓  先经过"格式器"
      格式器（FormatStrategy）
        └─ 普通格式 / 好看的格式 / 不格式化
             ↓  再交给"输出端"
           输出端（LogStrategy）
              ├─ 系统日志输出端
              └─ 文件输出端（DiskLogStrategy，安卓和苹果各写了一套）
```

**两层插拔**是它的设计核心：

- **日志器**决定"这条日志要不要、以什么级别输出"
- **格式器**决定"长什么样"
- **输出端**决定"送到哪里"

这个三层拆分是干净的，也是它能同时支持"只打系统日志"和"同时打系统日志 + 写文件"的原因。

## 第二章 值得抄的 9 个设计

### 2.1 用"快照数组"避免写日志时加锁 ★

**它怎么做的**：注册表内部维护一个列表，每次增删之后都把列表转成一个数组存到一个可变的共享变量里；写日志的时候直接遍历这个数组，**完全不加锁**（`LogcatLogger.kt` 第 44、62 行）。

**为什么好**：写日志是最高频的操作，如果每次都要抢锁，多线程下会互相等。用"不可变快照"这个手法，读的一方永远不用等，只有增删的时候才加锁。

**我们怎么用**：照抄。这是写高频日志的基本功。

### 2.2 同一条消息只拼一次 ★

**它怎么做的**：如果同时装了多个日志器，它会用一个临时变量把拼好的字符串缓存起来，第二个日志器直接复用（`Logcat.kt` 第 61–67 行）。

**为什么好**：避免重复做同一件费时的事。

**我们怎么用**：照抄，而且要推广——压缩、打码扫描这类重复劳动，也要保证每条只做一次。

### 2.3 惰性求值（消息用函数传进来，不用字符串）★

**它怎么做的**：接口是 `logcat { "消息" }`，消息是个函数。如果所有日志器都说"这个级别我不记"，那这个函数根本不会被调用，字符串也就不会被拼出来。

**为什么好**：**这是移动端日志最重要的一个优化。** 很多日志在正式版里是被过滤掉的，如果不管三七二十一先拼好字符串再判断要不要，白费的功夫会非常可观。

**我们怎么用**：照抄，而且这是我们"性能目标"能不能达标的一半答案——**真正拖慢速度的地方往往不是写文件，而是拼字符串**。

### 2.4 自动取标签，而且不花运行时代价

**它怎么做的**：入口是个内联扩展函数，能直接拿到 `this`，从中取类名当标签（`Logcat.kt` 第 64、92–102 行）。

**为什么好**：开发者一行都不用写标签。

**但要小心**（见 3.8）：它取的是**真实类名**，代码压缩之后会变。

### 2.5 安装查重 + "键控安装"

**它怎么做的**：同一个日志器实例重复安装不会静默重复，而是往那个日志器里打一条错误；另外有个"按钥匙安装"的机制，保证"只装一次"，而且**专门处理了一个很刁钻的竞态**——"上一个还正在关闭、这时候又来安装"（`LogcatLogger.kt` 第 82–110 行）。

**为什么好**：这说明作者是真被这些问题咬过的。日志库的生命周期竞态非常难测，他把它显式建模了。

**我们怎么用**：照抄思路，但**实现可以简化**——他用了一堆状态机，我们用一个清晰的"实例归属"模型就能覆盖大部分场景（见 3.7）。

### 2.6 可关闭的日志器 + 释放只执行一次

**它怎么做的**：抽象出一个"带资源的日志器"，用闩锁保证"释放资源"这个方法只会真正执行一次，其他人调用时都在等（`LogcatLogger.kt` 第 278–316 行）。

**为什么好**：重复释放文件句柄是经典 bug。

**我们怎么用**：照抄。

### 2.7 按剩余空间动态调整文件上限 ★

**它怎么做的**：文件上限不是写死的 20MB，而是有个"求解器"动态算：先查系统"实际还能分配多少空间"，扣掉预留的 50MB，再取其中 10%，最后还要保证不低于 256KB（`LogFileMaxSizeResolver.kt` 第 68–92 行）。安卓上它用的是系统的 `getAllocatableBytes`（比简单看剩余空间更准，因为安卓有存储预留机制）。

**为什么好**：**这条直接对应我们"硬盘满会把程序弄崩"那条约束。** 它没有用内存映射，所以不会崩，但它这个"根据剩余空间决定写多大"的思路是对的。

**我们怎么用**：思路照抄，用法不同——我们是用它来**决定"什么时候该换新文件"和"要不要暂停写入"**，而不是控制单片大小。另外它预留 50MB 给应用自身，这个"给别人留活路"的意识要保留。

### 2.8 用 expect/actual 隔开平台差异

**它怎么做的**：锁在安卓上用的是标准的线程同步、在苹果上用的是苹果的递归锁；取类名的写法两个平台也不一样，都通过 expect/actual 分开（`Platform.kt`、`Platform.android.kt`、`Platform.ios.kt`）。

**为什么好**：这是 KMP 里处理平台差异的标准姿势，没有更好的替代。

### 2.9 用 .def 文件把"难搞的 C 接口"包一层 ★

**它怎么做的**：苹果那边要把日志内容标记成"私密"（这样系统日志里不显示内容），这需要用到一段 C 代码。它写了一个 `.def` 文件，里面用 C 包了三个小函数（`os_log.def`）。文件里作者的注释明确写着：**`os_log_t` 这个类型从 C 传进 Kotlin 时类型对不上**（一边认为是指针，一边认为是对象），只好用 `void*` 绕过去。

**为什么好**：这段 34 行的文件，是"Kotlin 连 C 很别扭"这件事的**第一手证据**，同时也是标准解法——**把难搞的类型挡在 C 那一侧，只暴露最简单的东西给 Kotlin**。

**我们怎么用**：这条正好印证了我们架构约束里的"跨语言只用最基础的接口"。以后我们写 C 接口包装时，就照这个模式办。

## 第三章 必须绕开的 8 个设计

### 3.1 纯缓冲写文件：程序被杀就丢 ★★★

**它怎么做的**：日志先攒在内存的一个列表里，攒够 1 万个字符（默认）才真正写文件（`androidMain/DiskLogStrategy.kt` 第 169–172 行）。

**为什么不行**：**程序被系统杀掉的时候，攒在内存里还没写的那部分就全没了。** 而这恰恰是你最需要日志的时刻——用户反馈"App 崩了/闪退了"，你打开日志一看，最后几行是十分钟前的。

**我们怎么做**：用内存映射。日志写进映射区就等于进了系统缓存，进程被杀也不丢。这是我们和它**最本质的分界**。

### 3.2 装了全局崩溃处理器来补救 ★★

**它怎么做的**：因为它知道缓冲会丢数据，所以它接管了应用的**全局未捕获异常处理器**，在崩溃时抢着把缓冲刷到文件里（`androidMain/DiskLogStrategy.kt` 第 232–238 行），并且在关闭时再还原回去，还维护了一条"处理器链"。

**为什么不行**：
1. **它是全局状态**。任何一个组件装这种东西，就可能跟 App 自己、跟其他 SDK 抢；谁后装谁生效。它虽然做了"链式调用"和"关闭时还原"，但这套机制非常脆弱。
2. **它救不了真正致命的场景**：内存被系统回收（OOM 被杀）、原生代码崩溃、手机突然没电——这三种情况下那个处理器根本不会执行。而这三类恰好是最常见的。

**我们怎么做**：**我们不碰全局崩溃处理器。** 我们要解决的是"随时可读"的问题——文件本身一直是最新的，所以不需要在崩溃时抢救。这是从机制上解决问题，而不是打补丁。

### 3.3 每条日志都扫一遍目录 ★

**它怎么做的**：刷缓冲的时候，它对缓冲区里的**每一条**日志都调用一次"算出该写哪个文件"，而这个方法内部会**列出整个目录**去找最大编号（`androidMain/DefaultLogFileGenerator.kt` 第 57–64 行；苹果那边同样是列目录）。

**为什么不行**：这是"每条日志一次目录扫描"。好消息是它发生在后台线程，不会拖慢调用方；坏消息是它**严重限制了吞吐、还费电**。这不是错，是明显的浪费。

**我们怎么做**：文件编号、当前文件大小这些状态**在内存里维护**，只在真正切换文件时才去查一次磁盘。

### 3.4 字符和字节混着算

**它怎么做的**：缓冲区上限按"字符数"算（`message.length`），文件上限按"字节数"算（`file.length()`）。

**为什么不行**：中文一个字在 UTF-8 里占 3 个字节，两套尺子量同一件事，中文日志会严重算不准。

**我们怎么做**：**统一按字节算**。

### 3.5 没有压缩

**它怎么做的**：纯文本 `.log` 文件。

**为什么不行**：占地方、上传慢。日志文本的压缩比通常很高。

**我们怎么做**：压缩，但**不在调用方线程压**（那是后台的事）。

### 3.6 没有主动同步文件，掉电会丢尾巴

**它怎么做的**：写完把数据交给系统缓存就算完（`FileWriter` + `flush`），没有主动要求"立刻写到物理介质上"。

**为什么不行**：进程被杀能扛住（因为数据已经在系统缓存里了），但**手机突然没电会丢尾巴**。

**我们怎么做**：这条要**诚实**——我们不能承诺"掉电也不丢"（那要付出极大的性能代价）。做法是：文档里写明承诺边界（"进程异常终止不丢；设备突然断电可能丢最后 N 毫秒"），并在关键时机主动同步一次。

### 3.7 多日志器仍然建立在"全局注册表"上

**它怎么做的**：虽然支持装多个日志器，但那个注册表本身是**进程级的全局变量**——任何代码都能往里面装、也能把别人的卸掉（`LogcatLogger.kt` 第 38–40 行）。

**为什么不行**：这跟 Timber 的"全局只有一个"相比是进步，但**没有根本解决**"两个组件抢一个全局位置"的问题。组件化架构里这个隐患很现实。

**我们怎么做**：把"实例"做成一等公民——**日志器归创建它的人管，不放进共享的全局列表**。用户想全局共享，让他自己决定、自己持有，我们不替他做。

### 3.8 标签依赖真实类名，会被代码压缩改掉

**它怎么做的**：标签来自真实类名（安卓上是 `target::class.java.name`）。

**为什么不行**：正式版会做代码压缩混淆，类名会变成 `a.b.c`。用户线上看到的标签可能毫无意义。

**我们怎么做**：随包提供保留规则，或者更彻底——**在编译期就把标签固定成字符串**（这正好也符合我们"能用编译期解决的不放到运行期"的通用约定）。

## 第四章 它的编译期检查：能做什么、不能做什么

### 4.1 它怎么做的

用的是安卓官方的 lint 接口（`SystemLogUsageDetector.kt`，163 行）：

1. 声明"我只关心这几个方法名"：v / d / i / w / e / wtf / println
2. 每次碰到这些调用，判断一下"这个调用是不是指向安卓自带的日志类"
3. 是的话报错，并**提供一键修复**：把 `Log.d(标签, 消息)` 自动改写成它的 `logcat(标签) { 消息 }`，还会处理"带异常参数"的情况、自动加 import、整理格式

### 4.2 它的价值：证明了这条路是通的

**一键修复能做到这个程度，说明"lint 检查 + 自动改写"在工程上完全可行。** 我们做隐私检查时，基础设施可以直接照抄，不用从零摸索。

### 4.3 它的天花板：完全不看参数里是什么

它只判断"这个调用是不是安卓自带的日志接口"，**对参数内容一个字都不看**。

换句话说：**它查的是"你有没有绕开我"，不是"你有没有泄漏隐私"。**

这两件事差得很远。用户哪怕全部改用它的接口，照样可以把手机号、身份证写进日志——它的检查一点都不会报警。

### 4.4 我们怎么做才能真正查到隐私

这就落到我们架构约束第 10 条。具体三步：

**第一步：标出"敏感数据从哪来"。**
界面上用户输入的内容、设备标识、位置、通讯录、剪贴板、账号信息——这些是有数的、可以枚举的"源头"。

**第二步：在同一个方法内部跟踪这些数据被赋给了谁。**
比如用户输入的文本赋给了变量 `a`，`a` 又拼进了 `b`，`b` 被传进了日志——这一串要能跟下来。

**第三步：一旦它们进入了任何日志接口（包括系统自带的），报警并给修改建议。**

**为什么这个做法可行**：研究发现，**62.5% 的泄漏路径只有 2 到 4 句话，而且多半就在同一个方法里**。所以不需要做那种跨越整个程序的复杂分析——**只在一个方法内部跟踪就够了**，工程量差着量级。

### 4.5 一个关键技术判断：先不要碰编译器插件

- **lint 这条路的优点**：够用（能拿到源码结构）、跟着安卓构建工具走、不影响编译速度、可以做一键修复。
- **编译器插件那条路的优点**：能力更强（能看得更深）。
- **代价**：编译器插件要跟着 Kotlin 每个大版本改内部接口，**维护成本高得离谱**，一个人扛不住。

**结论：先用 lint 做到 90% 的效果。编译器插件留到第二版，而且只有在确实遇到 lint 做不到的场景时才上。**

## 第五章 一个被它的源码修正过的判断（很重要）

### 5.1 我发现的事实

iOS 那套写文件的代码里，**它没有自己的 C 或 C++ 核心**。它用的是 Kotlin/Native 自带的系统接口，直接调 POSIX 的"打开文件 / 写文件 / 关文件"（`iosMain/DiskLogStrategy.kt` 第 23–25 行引入，第 199–213 行使用）。

### 5.2 引申出来的结论

既然 POSIX 那套系统接口能直接从 Kotlin 调，那么**"内存映射"也是同一套系统接口里的东西**（它就是 `mmap`）。而安卓和电脑那边，Java 本身就自带内存映射（`FileChannel.map`）。

**所以——"要用内存映射"并不是"必须写 C/C++/Rust 内核"的理由。纯 Kotlin 也能做到"撑得过进程被杀"。**

这修正了我们之前的说法（之前我说"纯 Kotlin 用不了内存映射"，是不准确的）。

### 5.3 那写内核的真正理由是什么

只剩三个，而且**都是性能理由，不是能力理由**：

1. **每条日志的调用开销**：纯 Kotlin 方案里，拼装、压缩、敏感词扫描全在 Kotlin 侧做，对象分配多、跨语言调用虽然省了，但单条成本降不下来。
2. **零拷贝**：内核能做到"数据从字段直接进映射区"；纯 Kotlin 一般要经过字符串、字节数组这些中间对象。
3. **压缩、加密、敏感词扫描的绝对速度**。

### 5.4 这个修正为什么重要：它降低了项目风险

因为它意味着我们的路线可以**变成两级台阶**：

- **第一级**：先用纯 Kotlin 把"可靠性"这件事做扎实（内存映射、校验、恢复、轮转、配额、双时钟）——**这一级就能交付一个"撑得过被杀、格式公开、带打码"的可用版本**。
- **第二级**：如果第一级实测速度不够，再把"引擎"换成 C/Rust 内核，而**接口和格式不用变**（这正是我们把"接口标准"和"格式规范"提前定死的原因）。

换句话说：**纯 Kotlin 不是"退路"，而是"第一级台阶"。** 这样第一阶段那三个实验也可以先便宜地做出来，先去验证最不确定的"可靠性"，再去验证"性能要不要上内核"。

### 5.5 开工时要花 5 分钟确认的一件事

Kotlin/Native 自带的系统库里是否**直接**带着内存映射那几个函数。

- 带：直接用。
- 不带：写一个几行的 `.def` 文件包一层就行——**它的 `os_log.def` 已经给我们示范了标准做法**。

不管哪种结果，这条路都是通的，风险很小。

## 第六章 性能：它的选择 vs 我们的选择

它的公开材料里**没有性能数字**（跟腾讯 XLog、Log4a 比，这是弱项，因为没有数字就没有可信度）。

但我们可以从设计推断它的取舍，再对照 Log4a 那组公开测速（同一台手机上写 1 万条）：

| 做法 | 耗时 | 进程被杀后还在吗 |
|---|---|---|
| 纯写内存 | 13 毫秒 | 没了 |
| 内存映射 | 50 毫秒 | **还在** |
| 缓冲写文件（**它选的就是这个**） | 61 毫秒 | **没了** |
| 安卓自带日志 | 184 毫秒（而且没记完） | 没了 |

**结论很清楚**：它选的这个写法，比内存映射**只快一点点，代价却是"被杀就丢"**。

**我们的选择要反过来**：宁可慢那么一点点，也要"被杀不丢"。

因为——
- 快的这一点点，用户感知不到；
- 丢的那几行，恰恰是用户来投诉时你最需要的那几行。

## 第七章 它的构建与发布配置

这一章是把它的构建脚本、自动构建流程、发布配置逐份看完之后的结论。**这部分对我们的直接价值最大**，因为写代码可以慢慢来，但这些配置一旦定错，后面每发一次版都要痛一次。

### 7.1 它用的技术栈（比我们项目壳子旧，但是跑通的组合）

| 项 | 它的选择 |
|---|---|
| Gradle | 8.14.3 |
| Kotlin | 2.2.21 |
| 安卓构建工具 | AGP 8.12.3 |
| 安卓版本 | 编译/目标 35，最低 24 |
| JVM 目标 | 17 |
| 代码检查工具的版本 | 31.12.3（正好 = AGP 版本 + 23，**必须跟着 AGP 一起升**） |
| **NDK** | **完全没有用**（全仓库搜"ndk"零命中） |

**最后一行再次印证第五章的判断**：它整个仓库没有一行 C/C++ 核心，也没碰 NDK——它是纯 Kotlin 加系统自带接口做到的跨平台文件写入。

**对我们的意义**：它的组合比我们的项目壳子（Gradle 9.5 / AGP 9.3）旧一代，但它是**实际跑通过的**。我们要在 AGP 9 上重走一遍，得先确认"新版的 KMP 安卓库插件"在 AGP 9 上是否可用。

另外注意一个不寻常的地方：它用的跨平台界面库版本（1.7.0，2024 年 10 月）比 Kotlin（2.2.21）老很多，靠"界面编译器版本跟着 Kotlin 走"这个设置才没出事。**这种版本错配能在真实项目里长期存活**，说明构建配置的容错比想象中大——但这不是可以模仿的习惯。

### 7.2 模块结构

Gradle 里**只有 3 个模块**：

| 模块 | 是什么 |
|---|---|
| `logcat` | 要发布的那个跨平台库 |
| `logcat-lint` | 编译期检查（纯 Java 平台的模块，**从来不单独发布**） |
| `composeApp` | 演示 App（同时负责生产 iOS 的 framework） |
| `iosApp` | **不是 Gradle 模块**，只是个 Xcode 工程壳子 |

**值得抄的点**：检查单独成一个模块（对应我们架构约束里的 log-lint 独立模块），而且用的是**新的 KMP 安卓库插件**（`com.android.kotlin.multiplatform.library`），不是老的安卓库插件。这是新写法，值得作为我们的目标。

### 7.3 iOS 到底是怎么交付的（★ 修正了我们的一个假设）

这是本次分析里**最重要的一条发现**：

- **库模块里完全没有 framework 配置**：没有 XCFramework、没有 CocoaPods、没有"静态还是动态"的设置，一个都没有。
- 库是通过公共仓库发一个 **klib**（Kotlin 的编译产物）出去的。
- framework 是**由演示 App 生产出来的**，Xcode 靠一个叫 `embedAndSignAppleFrameworkForXcode` 的任务在构建阶段接进来。

**这条要修正我们之前的计划。** 我们之前写的是"第三阶段交付 XCFramework + SPM + CocoaPods 两种接入方式"。实际情况是分两种情况：

| 用户是什么项目 | 需要什么 | 我们要做多少工作 |
|---|---|---|
| **Kotlin 跨平台项目**（主流目标用户） | 从公共仓库拉 klib，**什么都不用额外做** | **几乎为零** |
| **纯 Swift 项目**（不用 Kotlin） | 需要 XCFramework + SPM 或 CocoaPods | 一大块打包工作 |

**所以这是一个范围决策**：第一版要不要服务"纯 Swift 项目"？

**我的建议是不服务**（第一版只服务 Kotlin 跨平台项目）。理由：纯 Swift 项目本来就不会选一个 Kotlin 写的日志库；为它们做打包，等于花了大约一成半的工作量去服务一小撮不会来的用户。这一条我已经加进待决策清单。

### 7.4 连 C 接口（cinterop）的三个实际细节

它只有一个 C 接口包装（就是 2.9 说的 `os_log.def`），但配置上有三个细节必须知道：

1. **只为苹果目标创建**，安卓那边不创建。
2. **必须把 .def 文件路径写死**。原因是默认规则会按"交互名"去找同名文件，而它的交互名叫 `osLog`、文件名却叫 `os_log.def`，默认找不到。
3. **必须打开"跨平台共享"开关**（`kotlin.mpp.enableCInteropCommonization`），否则共享代码里看不到它。

另外它开了 `-Xexpect-actual-classes` 这个开关（因为要用 expect/actual 写平台相关的锁）。

**这三条以后我们一定会用到**——只要碰 cinterop，就会踩同样的坑。

### 7.5 编译期检查是怎么发给用户的（★ 直接照抄）

这是它的配置里最漂亮的一手：

- 检查模块**不单独发布**，公共仓库里没有它的坐标。
- 它是通过 `lintPublish(project(":logcat-lint")) { isTransitive = false }` **塞进库的 AAR 里的**。
- 效果：**用户什么都不用配，装上库就自动有了检查。**（`isTransitive = false` 是为了不让检查工具的依赖污染用户的依赖表。）
- 注册做了双保险：一个是资源目录下的服务声明文件，一个是 jar 包清单里的属性。
- **一个坑**：它声明了 `api = CURRENT_API`，这等于把"检查"跟某个具体的 lint 版本绑死——**用户必须用足够新的安卓构建工具，否则检查可能不生效**。这种隐性版本要求一定要写进文档，否则会变成高频求助。

**对我们的意义**：我们的 log-lint 也应该走这条路——**用户改个依赖就自动生效，不用配任何东西**。这正好也是我们"零迁移采用"战略想要的形态。

### 7.6 发布配置

- 坐标、包名、版本号等信息**全写在 `gradle.properties` 里**，由第三方发布插件读取。
- 走的是**公共仓库的新通道**（老的已经停用），而且开了"自动发布"。
- 签名密钥**只在自动构建里注入**，不落进仓库（这点是对的，安全习惯好）。
- 只有库本体发布，检查模块跟着 AAR 走。

### 7.7 自动构建（CI）跑了什么、没跑什么

**跑了：**

| 机器 | 跑的内容 |
|---|---|
| Linux | 检查模块的测试和检查、库的编译、库的"宿主测试"（不碰安卓接口的那种）、库自己的代码检查、演示 App 的检查和打包 |
| 苹果电脑 | 三个苹果目标的编译、苹果模拟器上的测试 |

**没跑（这就是它的空洞）：**

1. **安卓真机测试从来没在 CI 里跑过**——只在本地手动跑。也就是说"真机上到底行不行"没有人自动守着。
2. **iOS 的 framework 从来没被真正链接过**：自动流程里没有编译 Xcode 工程这一步。意思是"打成 framework 之后能不能用"，自动流程抓不到，只能靠人手动验。

**对我们的意义**：这两条我们都是要补的。尤其第二条——**一个跨平台库最常见、最晚发现的故障就是"打包出来在用户项目里用不了"**，必须让自动流程真的编译一个"用户视角"的工程。

### 7.8 测试分层（这个结构值得抄）

| 层 | 跑什么 | 在哪跑 |
|---|---|---|
| 共享测试 | 纯 Kotlin 逻辑 | 三个平台 |
| 安卓宿主测试 | **故意只用 Java 的文件接口，不碰安卓接口** | 所以能在 Linux 上跑，不需要模拟器 |
| 安卓真机测试 | 只有必须用真机的才放这里 | 只在本地 |
| 苹果测试 | 用真实的临时目录和系统队列 | 苹果模拟器 |

**最值得抄的一点**：它**没有用"在电脑上假装跑安卓"那个框架（Robolectric）**，而是坚持"要么纯 Java、要么真机"。这个选择更干净——不会出现"电脑上跑过了、真机上挂了"的情况。

### 7.9 发版机制

- 用 release-please 这套：**根据提交信息自动决定版本号**（修复=小版本、新功能=中版本、破坏性变更=大版本）。
- 有个脚本检查**文档里写死的版本号和实际版本号是否一致**（文档不同步就报错）——这个做法很实用，值得抄。
- **最脆弱的一环**：它靠 `gradle.properties` 里的两行特殊注释来确定"版本号在哪"，这个标记一旦被误删，自动发版就静默失效。

### 7.10 配置层面：值得抄的 9 条

1. **检查模块塞进 AAR 里自动生效**（用户零配置）——见 7.5
2. 那个"忽略未启用目标"的开关**只在需要它的那台机器上开**，不写进全局配置
3. cinterop 的 .def 文件路径写死
4. 在 .def 里用 C 包装难搞的类型（见 2.9）
5. 打开"跨平台共享"开关，让共享代码能用 cinterop
6. Xcode 构建阶段的三个关键设置：标记为"总是过期"、关掉脚本沙箱、不配搜索路径
7. **依赖仓库做内容过滤**：只从谷歌仓库拉谷歌系的东西，其余走公共仓库——加快解析、避免被污染
8. 发版任务跑在苹果机器上（因为要出苹果产物）；发版流程不因为新提交而中断；非主分支上缓存只读
9. 文档与版本同步检查脚本

### 7.11 配置层面：必须躲的 9 条

1. **完全没有 API 兼容性门槛** ★★★——没有 `explicitApi()`、没有 API 转储文件、没有二进制兼容性检查。意味着**它随时可能悄悄改坏用户的代码而不自知**。这是我们最该补的一块（已写成架构约束第 17 条）。
2. **自动流程从不链接 framework、也不跑 Xcode 编译**——打包回归抓不到。
3. 没有提交一份共享的 Xcode 配置到仓库——别人接手时配环境困难。
4. 真机测试没有任何保护（不跑就没人知道）。
5. **库本身没有声明最低支持的苹果系统版本**（演示 App 声明了 18.2，库没有）——用户可能在老系统上踩坑。
6. `api = CURRENT_API` 把编译期检查和用户的构建工具版本隐性绑死。
7. 签名开关无条件写在配置里 → 本地想手动发个测试包会因为没密钥而失败。
8. 文档里写死了 Kotlin 版本号，而版本同步脚本不检查这一项 → 迟早过期。
9. 演示 App 里挂了一堆测试依赖却没有测试代码（小事，说明清理不及时）。

**这九条里，第 1、2、5 条是我们必须从一开始就避开的**——它们分别对应"用户的代码会不会被莫名其妙改坏""打包出来能不能用"和"老系统上会不会崩"。

## 第八章 我们跟它的边界在哪里

| 能力 | 它 | 我们 | 谁会赢 |
|---|---|---|---|
| 跨平台一套接口 | 做到了 | 做 | **打平**（这是及格线，不是卖点） |
| 能落盘 | 做到了，但被杀就丢 | 内存映射，被杀不丢 | **我们赢在可靠性** |
| 编译期检查 | 做到了，但查的是"有没有绕开我" | 查的是"有没有把隐私写进日志" | **我们赢在检查内容** |
| 自动打码 | **完全没有** | 三层打码 + 换代号 | **我们独占** |
| 格式公开 + 独立工具 | 没有规范、没有工具链 | 规范 + 命令行 + 独立实现 | **我们赢，但有个坑（见下）** |
| 发公共仓库 | 做到了 | 做 | **打平** |
| 性能数字 | 没有 | 公开可复现的测速 | **我们赢在可信度** |

### 一个必须正视的坑：它的"纯文本"反而是个优势

它的日志是**普通文本文件**，意思是——**用户拿任何一个文本编辑器就能直接看，零门槛。**

而我们的方案是"压缩 + 二进制 + 带校验"，**用户不能直接打开看**，必须用我们的工具。

所以在"方便看"这件事上，**它是赢的**。我们必须补上这个差距：

1. **命令行的体验要做到位**：一条命令就出结果，不要让人先装环境、再看帮助文档。
2. **提供一个"不压缩的明文模式"**：调试阶段用明文，正式发布用压缩。这样开发体验不吃亏。
3. **把账算清楚**：明确说明压缩换来的是什么（体积、上传速度、结构化的可处理性、打码之后仍然能对上号）。

**如果我们不主动解决"打开就能看"这个体验问题，用户会说"还不如用纯文本呢"。这是它给我们最实在的一个提醒。**

## 最后

这次体检最大的收获不是"学到了几个技巧"，而是两个判断：

**第一，它证明了一个人能做出"跨平台 + 能落盘 + 带编译期检查 + 发到公共仓库"的库。** 这是个正面的可行性证据——我们担心的事情，别人已经用一个人的力量走通了一遍。

**第二，它**没做**的那两件事——"高可靠的落盘"和"隐私保护"——正好是我们要做的全部。**

它既是我们的参照物，也是压力来源：它已经在公共仓库、已经在更新、已经想清楚了要做编译期检查。**如果它哪天补上内存映射和打码，我们想做的事就被覆盖了。**

所以我们的路只有一条：在这两件它没做的事上，做到它做不到的深度。
